# 游戏数据维护

改游戏数据（`packages/config/data`）和写改玩家数据的迁移时要注意的事。

## 新街道数据（问题记录 284）

新街道的菜谱、食材、勋章由另一个 agent 生成，放在仓库外的 `data/新街道菜谱`，菜名译名在 `data/i18n`。那边改了数据后：

1. 重跑导入：`pnpm -F @dt/config import-streets`
   - 替换 `data/master/` 三份主表里 `src` 为 `streets` 的条目（其余条目和顺序不动），整份替换 `data/designed/streets_new.json`；8~10 品级按老数据的换料频率重新生成（种子 284，结果固定）。
   - 已经不存在的新菜谱译名会自动删掉；新增的街道会自动补进 `street_medal_map.json`（勋章 id = 92000 + 街道 id）。
   - 上次导入过的新菜谱 id 这次没了、或者换了街道时，脚本什么都不写、直接退出（多半是那边顺移了 id）。确认确实要删或改，再加 `--allow-removed` 重跑。
   - 去掉一条街时，`street_medal_map.json` 里那一行要手删（构建会报错提醒）。
2. `pnpm -F @dt/config build`，构建会检查菜谱、用料、勋章对照的一致性。
3. **新菜谱 id 已经上线，要求那边固定 id，不能顺移。** 改了 id 等于删掉老菜、加一道新菜，学过的店会丢记录。

## 道具、食材、菜谱的定义（重新编号 PR 1）

- 全部在 `packages/config/data/master/`：`goods.json`、`foods.json`、`cookbooks.json`，每条一行，`src` 写来历。
- 原版数据集（`../analysis/dataset`）不再同步这三类，也不再同步带编号的特色菜用料、老虎机奖品、菜场竞猜食材（原版是旧编号）；原版获取途径表 `dataset/goods_sources.json` 仍同步，按原版（旧）编号，工具按 `legacyId` 对上。
- 改定义直接改主表；新街道的条目由导入脚本整块替换，不要手改。
- 一番赏主题、基金勋章、新手大礼包、厨具套装和强化表仍在 `data/game/` 各自的文件里，只引用主表的编号。
- 菜谱的 `slot` 是学会记录（`restaurant_cookbooks.levels`，每道菜一个字节）里的存储位（重新编号 PR 3）：只增不复用，下一个可用的写在 `data/game/cookbook_slots.json`。新街道导入时已有的菜保留原存储位、新菜从那里往后分；手加菜谱也要这样分，并把 `next` 加上去。删菜时存储位空着，不要给别的菜用（老店那一位上可能还有品级）。删掉的菜以后又加回来时，导入会给它分新的存储位：老店在旧位置上的品级不会自动接上（店里的已学计数却还算着它），要接上就在主表里把它的 `slot` 改回原来的值。
- 代码里取学会记录一律经 `cookbookIndex.slotOf`（`gradeOf` / `setGrade`），不要拿菜谱编号当下标；服务端测试的配置故意把存储位倒过来排，按编号取的代码会让测试失败。

### 编号规则（2026-10 重新编号）

- **道具**：5 位，按类别分段（1 消耗品和功能道具、2 礼包、3 设施、4 厨具、5 宝石、6 荣誉、7 纪念品和手办），段内按小类从整百起。小类定义在 `data/game/goods_groups.json`（`key`、名字、起始 `base`、容量 `size`）。加道具：选一个小类（没有合适的就新开一个整百段，不能和已有的重叠），编号取该小类已用的最大编号 + 1，`group` 填小类的 key。
- **食材**：等级 × 1000 + 序号，取该等级已用的最大序号 + 1；万能食材 9001~9005。以后改了食材等级，编号不跟着改。
- **菜谱**：100000 + 街道 × 1000 + 序号，取该街道已用的最大序号 + 1；`slot` 取 `game/cookbook_slots.json` 的 `next`，再把 `next` 加 1。菜谱换街道，编号不跟着改。
- 按“基数 + 等级”算的保持连续：N 级食材兑换券 10101~10105（`GOODS.levelTicketBase`）、食材随机券 10201~10205（`NEWBIE.foodVoucherBase`）、残卷碎片 10801~10806（`GOODS.fragmentBase`）。街道勋章 = 60000 + 街道编号；一番赏月度手办 = 71000 + 月份 × 10 + 档位（A 1、B 2、C 3、最后赏 4）。
- 构建会检查：道具在所属小类的号段里、小类不重叠、食材在 1001~9999、菜谱在 100001~199999、`legacyId` 不重复。
- `legacyId` 是重新编号前的编号，只在当时已有的条目上有；新加的不填。它给旧链接跳转（Wiki、开放接口）、原版获取途径（`dataset/goods_sources.json` 按旧编号）和新街道导入（外部数据仍是旧编号）用。对照表原件在 `data/renumber/map.json`，审阅报告在 `docs/design/重新编号对照.md`。

## 改已学食谱的迁移

- 删菜、移街用迁移 0039 的 `reviseCookbooks(db, deleted, moved)`：按清单清掉已学字节、调整已学计数和各街计数，并删掉点了被删菜、还能接的外卖单。0040 也复用它。
- **改这个函数要保证不传 `restIds` 时行为不变**：已经跑过的迁移在新库上还会再跑一遍。`restIds` 只给测试用，免得测试改到共享测试库里别的店。
- 0039 一次把所有店的已学记录读进内存（开发库 1366 家约 25MB）。以后在大库上跑类似迁移，要改成在 SQL 里过滤或分页。

## 下架道具、食材（问题记录 367）

用不到的道具、食材不删定义，记进下架名单 `packages/config/data/game/retired.json`：

- 玩家手上已有的照常显示、能用能卖；不再从任何途径产出：退出商店、随机奖励池、各等级食材池（菜场、合成、神殿、礼包、兑换券都从这里抽）、交易所和开放接口（Wiki）。
- 镇长兑换、声望商店、星愿里“换到 / 买到 / 许到”的东西下架后，这几条在构建时自动去掉，不报错（问题记录 501）；翻译表里多出来的条目不算错。
- 构建时检查：下架的东西还被奖励、礼包、兑换的材料、食谱、特色菜、区服数值里的奖励、搬家发的街道勋章引用，或者代码里用到（`itemRefs.ts` 的 `CODE_GOODS`），构建报错并列出引用处。
- 存在数据库里的奖励：后台保存区服数值、活动、兑换码、邮件时拒绝已下架的编号；**下架之前已经存好的不会自动改**——已开的活动、兑换码照发，区服数值覆盖照用（服务器启动时对这些区服写警告日志）。下架前先在后台查一遍。
- 当天已经进货的菜场、已经刷出的商店特价是存好的，下架的东西要等下一次刷新才消失。
- 名单用道具整理工具改：`pnpm -F @dt/server items`（默认端口 5199，只在本机监听），打开 http://127.0.0.1:5199/。
  - 每行列出来源、用途、原版来源（`dataset/goods_sources`）和有条件才成立的说明（“只能靠菜园获得”“食谱只在品级上限调到 10 时用到”）；可以按“没有来源”“没有用途”等筛选。
  - 来源按配置和服务端的规则函数算（`apps/server/src/items/analyze.ts`，默认区服数值）。新加了产出食材或道具的玩法，要在那里补上，不然工具会误报“没有来源”。
  - 勾选、写备注后保存：先按新名单构建一次，过不了就不写文件、在页面上列出原因。
- 保存后 `pnpm -F @dt/config build`，再重启开发服务器生效；提交 `retired.json`。
- 要恢复：在工具里取消勾选再保存。
- 后台“道具整理”页（问题记录 429）用的是同一份分析（`analyze.ts`），只读，和本地工具的差别：按线上配置算（已下架的看到的是下架以后的来源），没有原版获取途径和下架备注，只用默认区服数值。analyze.ts 漏了来源，两边都会误报。

## 商店价格和上下架（问题记录 483）

银币价、钻石价、银币商店上下架、今日特价池、黑市池不直接改道具表和设计表，改 `packages/config/data/game/shop.json`，构建时盖在上面：

- `goods` 每项只写改过的字段（`coin`、`diamond`、`onSale`），可以带备注；`pools.special`、`pools.black` 写了就整份替换设计表里的那个池。
- 银币价同时是回收价（× `tuning.shop.sellRate`）、今日特价折扣价、道具价值分析的基准。改价前想一想会不会买了再卖、捆了再卖赚银币（`build.test.ts` 有捆绑道具的检查）。
- 构建时检查：不存在的道具、同一道具写两次、已下架的上架、黑市池里没有钻石价、特价池里没有银币价，都报错。
- 用商店整理工具改：同一个工具 `pnpm -F @dt/server items`，打开 http://127.0.0.1:5199/shop（道具整理页顶上有入口）。浅黄底是和原版不同的；保存时只写和原版不同的字段、改过的池子和备注，先构建一次，过不了不写文件。
- 保存后 `pnpm -F @dt/config build`，再重启开发服务器生效；提交 `shop.json`、发版后线上生效。不分区服，所有区服一样。
