# 性能：怎么测、测到了什么

质量期第 ③ 批（2026-10-05）建立的做法。性能优化是长期工作：每次改动先测、改完再测，结果记在这里。

## 测量工具

### 1. 每个请求的查询统计（Server-Timing）

服务端环境变量（`apps/server/.env.development` 已经打开）：

| 变量 | 作用 |
|---|---|
| `DB_QUERY_STATS=true` | 每个响应带 `Server-Timing: db;dur=<查询毫秒>;desc="<条数> queries", app;dur=<总毫秒>`。浏览器开发者工具的 Network → Timing 里能直接看到 |
| `DB_SLOW_MS=100` | 超过这个毫秒数的查询往 stderr 打一行 `slow query` 警告（带语句），API 和 worker 都算；0 = 不记 |

两个都默认关闭；关闭时不挂回调，没有额外开销。实现见 `apps/server/src/infra/queryStats.ts`。

注意：
- 查询是并发发出时，`db` 是各条耗时的和，会大于 `app`；
- 事务的 `begin`、`commit` 也各算一条；出错的查询不计；
- `db;dur` 是每条查询耗时相加：查询一起发的接口（餐厅总览、菜场、酒吧、一番赏、神殿、小镇）会大于实际等待的时间，甚至大于 `app`，看 `app`；
- `app` 到发送前为止，不含压缩。

### 2. 接口压测

```bash
# 开发服跑着（pnpm dev）时，用一个玩家账号依次请求常用接口
pnpm -F @dt/server bench:api <用户名> [区服 id]
# 只测几个接口、多采样
PATHS=/restaurant/overview,/task/list N=30 pnpm -F @dt/server bench:api <用户名> 1
```

在 Git Bash 里设 `PATHS` 时要加 `MSYS_NO_PATHCONV=1`，否则以 `/` 开头的值会被改写成 Windows 路径。

e2e 测试号的密码都是 `secret123`；数据多的号可以按等级从开发库里挑。

看服务端的数（`app`），不要看客户端计时：Windows 本机回环加计时器粒度，每个请求在客户端会多出 15 毫秒左右的固定开销。

### 3. 查询条数预算测试

`apps/server/src/perf/budget.test.ts` 给常用接口设了查询条数上限（新开的店、没有活动的区服、第二次请求）。改功能让条数变多时这条测试会挂：先想想能不能并进已有的查询，确实需要再调预算。

单个功能也可以用 `test/queries.ts` 的 `queryCounter()` 数查询，例如活动列表“条数不随活动个数增长”、交易所“锁店事务里只读一次参考价”。

### 4. 周期任务耗时

`job_run` 表记着每次周期任务的开始和结束时间，结算的 `stats.ms` 是整轮耗时：

```sql
select job, count(*), round(avg(extract(epoch from finished_at - started_at)) * 1000) avg_ms,
       round(max(extract(epoch from finished_at - started_at)) * 1000) max_ms
from job_run where finished_at is not null and started_at > now() - interval '2 days'
group by job order by avg_ms desc;
```

## 2026-10-05 的测量（开发服，Windows + Docker 的 Postgres）

开发库：1,464 家店，一服 86 家在营业。玩家号 eut6s3wg（60 级、4 星），每个接口热 2 次后采 20~30 次，服务端耗时中位数：

| 接口 | 改前 | 改后 | 查询条数 | 做了什么 |
|---|---|---|---|---|
| `/restaurant/overview` | 30.6 ms | 10~12 ms | 11 | 互不依赖的查询一起发（一个请求同时占约 9 个连接） |
| `/task/list` | 26.3 ms | 12~13 ms | 12 → 5 | 店铺的 8 项计数合成一条查询（可能在事务里跑，不能并发） |
| `/activities/summary` | 22.6 ms | 9.5~10 ms | 35 → 7 | 所有活动的进度、结算、今日计数一次读完，条数不随活动个数增长 |
| `/activities` | 20.8 ms | 9.8 ms | 35 → 7 | 同上 |
| `/world/catalog` | 每次 289KB | 没变时 304、0 字节 | 0 | 按语言序列化一次，带 ETag |

其余常用接口服务端都在 6~20 毫秒，查询 1~10 条，暂时不用动。开发环境里一条查询大约 1~2 毫秒（Docker 的网络），生产环境会快不少。

结算：每家店约 4 毫秒（分批并发），每 4 分钟一轮；一个区服上万家店一轮十几秒，暂时不是瓶颈。

## 2026-10-06 的测量（第二轮，只测没改）

开发库：1,497 家店。同一个玩家号 eut6s3wg，每个接口热 2 次后采 20 次。

**接口**：服务端耗时中位数都在 4.5~18 毫秒，查询最多 11 条，比 10-05 改完时没有变慢。最慢的一组：

| 接口 | 服务端中位数 | p95 | 查询条数 |
|---|---|---|---|
| `/market/view` | 18.3 ms | 21.0 ms | 10 |
| `/bar` | 17.8 ms | 21.1 ms | 10 |
| `/kuji` | 17.6 ms | 20.9 ms | 9 |
| `/temple` | 16.6 ms | 19.0 ms | 9 |
| `/town` | 16.4 ms | 22.2 ms | 10 |
| `/equip/overview` | 14.8 ms | 18.3 ms | 8 |
| `/restaurant/overview` | 12.5 ms | 29.4 ms | 11 |

这几个的查询多半互不依赖、却一条接一条地发（例如神殿：今日伤害、是否击杀、持有道具、试炼、厨具、加成、喂养各一条）。backlog 第 ⑦ 批改成互不依赖的一起发（查询条数不变），同样采 30 次：

| 接口 | 改前 | 改后 |
|---|---|---|
| `/market/view` | 18.3 ms | 12.7 ms |
| `/bar` | 17.8 ms | 9.1 ms |
| `/kuji` | 17.6 ms | 12.4 ms |
| `/temple` | 16.6 ms | 8.6 ms |
| `/town` | 16.4 ms | 8.2 ms |

一番赏的列表在买券、抽签的事务里也会用到，事务里照旧一条接一条（同一个连接上并发没有好处）。生产环境一条查询更快，实际收益比开发服小。

**周期任务**（`job_run` 近两天）：结算平均 105 毫秒一轮、最长 1.6 秒；其余任务平均都在 1 秒以内。最重的 `honor-effects-resync`（约 1 秒）只在勋章数值改了以后每个区服跑一次，不用管。

**目录接口**：`/world/catalog` 第一次约 90 KB（压缩后），之后靠 ETag 不再下载。

**前端首屏**（`pnpm -F @dt/web build`，压缩后）：

| 文件 | 大小 |
|---|---|
| 入口 JS | 133 KB |
| CSS（Bootstrap + 图标的类） | 48 KB |
| 图标字体 `bootstrap-icons.woff2` | 134 KB |
| 其余四种语言包 | 各约 55 KB，按需加载 |

图标字体是整套 Bootstrap Icons（两千多个），代码里只用到 73 个，而且名字都是写全的 `bi-xxx`。backlog 第 ⑦ 批改成只带用到的：`pnpm -F @dt/web icons`（`scripts/gen-icons.mjs`）扫代码生成 `src/styles/icons.css` 和子集字体，`src/icons.test.ts` 核对用到的都在子集里。图标字体 134 KB → 7.9 KB，CSS 48.5 KB → 35.6 KB，首屏少约 139 KB；原来给老浏览器的 .woff（180 KB）也不再打包。

## 2026-10-08 的测量（第三轮：线上只读检查 + 开发服）

### 线上（1 核、955 MB 内存，4 家店，库 29 MB）

- 周期任务都很快：结算平均 34 毫秒，最长的 `honor-effects-resync` 1.7 秒（只在勋章数值改了以后跑）；缓存命中率 99.99%。
- 容器里 Redis 往返 0.36 毫秒、Postgres 0.45 毫秒（开发机都是 1.7~1.9 毫秒：Windows 上的 Docker 网络。开发服每个请求查会话、限流要往返 3~4 次，所以 `/time` 这种不查库的接口在开发服也要 7 毫秒，线上没有这段开销）。
- **连接池每 10 秒断一次**：pg 默认空闲 10 秒就断开连接，线上人少，Postgres 启动 3.9 天新建了 15.4 万次连接（约 2 秒一次）；新建一条要 14 毫秒（最慢 74），复用只要 0.45 毫秒。健康检查 `/readyz` 只有一条 `select 1` 和一次 ping，却要 22 毫秒。→ 改成每个进程最多留 4 条常驻，其余空闲 1 分钟再断（`poolOptions`）。服务器内存小，不留太多。
- **跨域预检每次都发**：前端每个请求都带 `x-device-id`，接口在单独的域名，浏览器要先发 OPTIONS 预检。原来没写 `Access-Control-Max-Age`，Chrome 只缓存 5 秒、按网址分开记，线上几乎每个请求都多一次往返（从外面量一次往返 60~160 毫秒）。→ 缓存 2 小时（Chrome 的上限）。
- **静态文件只缓存 4 小时**：Cloudflare Pages 默认 `max-age=14400, must-revalidate`，过后每个文件都要回源确认。文件名带哈希，→ `public/_headers` 里给 `/assets/*` 设一年、immutable；`index.html` 照旧每次确认。
- **首屏**（没登录，冷缓存）：首次绘制约 1.75 秒，顺序是入口 JS（145 KB）→ `/account/me`（642 毫秒，含预检和第一次连接接口域名的 DNS、TLS）→ 登录页的代码。→ 页面头部加 `<link rel="preconnect">` 提前连接口域名（构建时有 `VITE_API_BASE` 才加，`src/build/preconnect.ts`）。热缓存时首次绘制 0.18 秒。

### 开发服（1,569 家店，171 MB）

**接口**：用 eut6s3wg 测了 66 个 GET 接口，每个 15 次，服务端中位数都在 7~33 毫秒，查询最多 11 条；扣掉上面说的开发机往返开销，和 10-06 一样。

**查询计划**：进程内起 API、把这 66 个接口各请求一遍，抓下 154 条不同的语句逐条 EXPLAIN，整表扫 1,000 行以上的只有 4 条：等级排行、收购身价榜（本来就要排整个区服，有进程内缓存）、邀请页按 `invited_by` 查账号（没有索引，只有打开邀请页时查，1 万个账号也就一两毫秒，不改）。

**周期任务**：结算中位数 111 毫秒、p99 613 毫秒；最长的 5.6 秒和外卖订单的 4.5 秒是同一时刻（开发机卡了一下），不是代码问题。

**页面的串行请求**：登录后在应用里切到 31 个页面，记每页发了哪些接口、几轮一个等一个。改了几处互不依赖却一个接一个读的：

| 页面 | 改前 | 改后 |
|---|---|---|
| 首页（概况 → 任务 → 白食） | 3 轮 | 1 轮 |
| 食谱（餐厅 → 列表 → 下一星要求） | 3 轮 | 2 轮（记着本店时按记着的街道先读列表） |
| 收益记录、餐厅信息、收购 | 2 轮 | 1 轮 |

线上每少一轮就少一次往返（改预检之前是两次）。

**前端包**：入口 JS 压缩后 145 KB（10-06 是 133 KB，功能多了），其中简中语言包约 100 KB（压缩前）、Vue 72 KB、zod 56 KB、vue-router 26 KB，没有混进来的大块；其余四种语言包各约 66~74 KB，按需加载。

## 看过但没改的

- 登录记录清理（`cleanLoginTrace`）每 6 小时扫一次全表：这张表上线后几万到十几万行，扫一次几十毫秒；为它加 `last_seen` 索引，每次登录都要多维护一个索引，不划算。
- 后台经济统计实时算今天和昨天：热的时候一天约 60 毫秒，只有管理员偶尔看。
- 交易所成交时每个挂单方多查一次店铺（emitActionFor）：一笔成交通常一到三家，不值得改撮合流程。
- （10-08）底部导航每次切页都读一次好友申请数（红点），很多街道页还会读一次嘻哈：和页面数据一起发，不拖慢页面，只是多一个请求。
- （10-08）首页和公告弹窗各读一次公告：一起发，不拖慢。
- （10-08）线上内存：4 个 node 进程各 50~70 MB，交换区用了 300 多 MB（大头是 dockerd）；玩家多了以后可以考虑 2 GB 的机器，或把 worker 减到 1 个（两个 worker 时靠数据库的咨询锁选主节点，只有主节点跑任务，另一个只是备用）。用户定减到 1 个（ops/1008）。
- （10-08）厨具页的“加点”、小镇的新闻在数据回来后才读（子组件、标签），属于按需加载，不算串行。
