# 特色菜限速方案（2026-11-21）

给实现的人看。读完这一篇就能动手，不需要翻之前的讨论。

## 1. 问题和目标

收益模型改版（2026-11-19，厨艺钱）上线后，高等级特色菜在卖的时候，收入的一多半来自特色菜，而且这笔钱和学了多少菜无关。

线上数据（11-19 到 11-21，20 家店 9413 轮）：

- 4、5 级特色菜在卖时，特色菜占当轮收入的 45%~59%。例：2 号店没特色菜时每轮 15,084，5 级菜在卖时 38,090。
- 原因：一桌满意的挑剔顾客吃 2 份。2 号店这一桌的厨艺钱是 258，5 级菜 2 份是 576。
- 各等级按菜场原价、不算店铺加成都还赚钱，但 3~5 级很薄（每锅卖得 ÷ 成本 = 1.07 / 1.18 / 1.12），没有压价空间。

目标：

1. 特色菜仍然赚钱：每份卖价、卖出倍率、每锅总收入都不变。
2. 特色菜不压过主线：在卖时，特色菜的钱最多是厨艺钱的 0.5 倍左右。
3. 学菜越多，特色菜卖得越快。

做法：不改价钱，只改每轮吃掉的份数。

## 2. 现在的规则

代码在 `apps/server/src/modules/settlement/tables.ts`。

- 满意的挑剔顾客：每桌吃 2 份，每份付 `每份价值 × 卖出倍率 × (1 + mcCoinRate)`。在逐桌循环里当场吃。
- 普通顾客：循环结束后挑 ⌊普通桌数 × `normalSpecialShare`(0.5)⌋ 桌，各吃 1 份，付 `normalSpecialPriceRate`(0.5) 成。
- 章鱼哥：吃 `squidwardPortions`(4) 份，不付钱，带长笛时给经验。
- 未满意的挑剔顾客、其他顾客：不吃。
- 一批剩得不够时，先到先得（挑剔顾客和章鱼哥在循环里，先于普通顾客）。

## 3. 新规则

记：

- `F` = 这家店本轮的厨艺钱（`fameCoin(...)` 的结果，和每桌付钱用的是同一个数）
- `p` = 每份卖价 = `special.price × saleRates[level − 1] × (1 + mcCoinRate)`
- `X` = 新配置 `settlement.specialFameCap`，起步值 0.5

### 3.1 每轮应卖份数（带小数）

- 挑剔：`满意的挑剔桌数 × min(2, X × F ÷ p)`
- 普通：`普通桌数 × min(normalSpecialShare, X × F × fame.normalShare ÷ (p × normalSpecialPriceRate))`

含义：每桌特色菜的钱，期望值不超过这桌厨艺钱的 X 倍。挑剔桌的厨艺钱是 F，普通桌是 F × normalShare。

菜便宜时两个 min 都取前一项，结果和现在完全一样。

### 3.2 零头留到下一轮

不逐桌取整，不掷骰子。挑剔和普通各记一个零头，存在这一锅（`mc_cook`）上：

1. 本轮实卖份数 = ⌊应卖份数 + 上轮零头⌋
2. 新零头 = 应卖份数 + 上轮零头 − 实卖份数（一定在 0 到 1 之间）
3. 这一批剩余不够时，能卖多少卖多少，这锅卖完，零头作废
4. 新下锅的一批零头从 0 开始

### 3.3 整数份数怎么分到桌

- 挑剔：实卖 N 份、满意的挑剔桌 m 桌。每桌先给 ⌊N ÷ m⌋ 份，余下的按桌号从小到大各多 1 份。每桌最多 2 份（按 3.1 的算法 N 不会超过 2m）。不新增随机数。
- 普通：实卖 N 份就挑 N 桌各吃 1 份，挑法沿用现在的随机挑选。

因为满意的挑剔桌数要整轮算完才知道，挑剔顾客吃特色菜要从逐桌循环里挪到循环之后，和普通顾客的处理放在一起。挪动后每桌的 `last`（银币、经验、`mcNum`、`mcId`）和整轮合计都要补上，写法参考现在普通顾客那一段。

### 3.4 不变的东西

- 每一份卖出去都按 `p` 全额收钱（普通顾客仍是 `normalSpecialPriceRate` 成）。**不允许把某桌的特色菜钱截到上限**，那样会让一锅的总收入变少。
- 每份给的经验不变（挑剔每份给菜的等级，普通每份 1）。
- 章鱼哥不变：照吃 4 份，不受上限限制，不占挑剔的份额，不动零头。
- 一批不够时的先后：章鱼哥（循环里）→ 挑剔 → 普通。
- 时令值仍按挑剔顾客和章鱼哥吃掉的份数算（`specialPicky`），算法不改，只是份数变少。
- 满足的挑剔顾客银币加成（`spCoinRate`）仍然不乘特色菜。
- `mysterious.saleRates`、`normalSpecialShare`、`normalSpecialPriceRate` 的值都不动。

### 3.5 不做保底

学菜很少的店做很贵的菜会卖得很慢。例：1 星小店（厨艺钱 54）做每份卖 208 的 5 级菜，每桌平均 0.13 份，一锅 555 份约要 55 小时，期间不能下新锅。这是已知的，本期不加“每轮至少卖几份”的保底（用户 2026-11-21 定）。

## 4. 配置和数据

- 新配置 `settlement.specialFameCap`：默认 0.5，区服可覆盖。小于等于 0 表示不限速，行为和现在完全一样（用来回退）。
- `mc_cook` 加两列，记挑剔和普通的零头，`double precision not null default 0`。已有的批次按 0 处理。
- 结算读这两列、写回这两列，和扣份数（`consumeSpecial`）在同一个事务里。
- 上线前核对线上区服覆盖：现在有 `mysterious.saleRates [1.2, 1.4, 1.7, 2.1, 2.2, 1]` 和 `levelBonusPerLevel 0.02`，都保留。

## 6. 连带改动

- **结算**：`settlement/tables.ts`（挑剔吃特色菜挪到循环后、份数算法）、`types.ts`（输入带零头、结果带新零头）、`runner.ts`（读写零头）。
- **迁移**：`mc_cook` 加两列。
- **配置**：`packages/config/src/tuning.ts` 和 `data/game/tuning.json` 加 `specialFameCap`。
- **特色菜界面**：`mysterious/service.ts` 现在返回 `saleRate`。加上“现在每桌挑剔顾客平均吃几份”，让玩家看得到学菜多卖得快。文字要有简中、英、法、西，繁中由脚本生成。
- **规则说明**：`docs/rules/收益与加成.md` 里特色菜卖法那一段，以及游戏内帮助里对应的文字。
- **模拟**：`sim` 里如果算了特色菜收入，按新算法改；没算就不动，在 PR 里说明。
- **测试**：`settle.test.ts`、`shiling.test.ts` 里依赖“每桌吃 2 份”的断言要改。挑剔吃特色菜挪位置会改变取随机数的先后，固定种子的测试结果会变，逐个确认是预期变化。

## 7. 本期不做

- 保底（见 3.5）。
- 让份数随厨艺值涨得比厨艺钱更快。现在厨艺值翻倍只快 27%，先看线上占比再定。
- 调卖出倍率、每锅份数、食材价格。
- 未满意的挑剔顾客吃特色菜。

## 8. 验收条件

1. **不亏**：任何情况下，一锅卖出的银币（乘店铺最终加成之前）= 挑剔吃掉的份数 × `p` + 普通吃掉的份数 × `p` × `normalSpecialPriceRate`。章鱼哥吃的份数不付钱，和现在一样。写成测试，覆盖 `p` 远大于 `X × F` 的情况。
2. **便宜的菜不变**：`p ≤ X × F ÷ 2` 且普通那一项也没碰到上限时，每轮卖出的份数和现在一致。
3. **零头**：连续多轮后，累计实卖份数和累计应卖份数相差不到 1 份（挑剔、普通分别算）。零头始终在 0 到 1 之间，换锅后归零。
4. **学菜不亏**：其他条件相同，厨艺值更高的店每轮应卖份数不会更少。
5. **回退**：`specialFameCap ≤ 0` 时每轮卖出的份数、银币、经验和改动前一致（取随机数的先后变了导致的差异除外，要说明）。
6. **线上副本重放**：用线上库副本跑，列出第 5 节那张表的实际值。4、5 级菜在卖时特色菜占当轮不超过 40%；1、2 级菜的卖出速度变化不超过 10%。超出的店逐家说明。
7. **时令值、经验**：列出重放里特色菜经验和时令值的变化幅度，不设门槛，写进 PR。
8. 全部测试和构建通过。

## 9. 流程

- 从 main 开新分支，提 PR，不部署。
- 所有新数值都能用区服覆盖调。
- PR 里列出：第 6、7 条验收的实际数字、因随机数先后改变而更新的测试、模拟是否受影响。
