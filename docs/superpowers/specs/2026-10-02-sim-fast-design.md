# 快速数值模拟（问题记录 160）设计

日期：2026-10-02
状态：待用户审阅

## 1. 背景和目标

现有模拟器（`pnpm sim`，子项目 2A 设计 §8）的工作方式：
- 用一次性库 `dt_sim`；
- 每 4 分钟推进一轮，跑真实的定时任务和结算；
- 机器人直接调用真实的服务代码。

实测 2 天、3 个机器人用 65 秒，约每天 30 秒。默认的 30 天、9 个机器人要 15 分钟以上，调一次数值等太久。

目标是**秒级迭代主线成长**：改一个数值，十几秒内看到三种玩家的成长节奏和经济是什么样。现有的全真模拟器保留不动，用来做核对。

## 2. 用户已确认的裁定

| # | 问题 | 裁定 |
|---|---|---|
| 1 | 用途 | 秒级迭代主线成长：主线按真实规则算；旁支玩法按每天平均产出折算；全真模拟器保留，用来核对 |
| 2 | 做法 | 内存里的快速模型（方案 A）：结算直接调用游戏的纯函数；机器人的成长动作在内存里用游戏现有的规则函数重写 |
| 3 | 旁支产出 | 一张可以改的产出表，按来源和等级段写每天平均产出；初值由实现者估算并写明依据；报告单列旁支收入占比 |
| 4 | 对比方式 | 一次跑多套数值，同一份报告并排对比 |
| 5 | 机器人 | 每种画像几十个（默认 20 个），报告给中位数和 10%、90% 区间 |

## 3. 范围

**模拟的内容**（主线，按真实规则）：
- 每 4 分钟一轮的结算，包括银币、经验、耗油、顾客、掉落、蟑螂、老鼠、痞老板、停业；
- 升级，体力恢复，自动加油；
- 机器人的上线动作：签到、任务和活跃奖励、加点、加油、灭自己店的蟑螂、摆设施、升星、扩油壶、买餐桌、在菜场和商店买食材、学食谱和升级食谱、合成多余食材；
- 世界状态：天气、蟹老板巡街、节日倍率、痞老板选店；
- 菜场按真实时间上新，机器人共用货架。

**折算的内容**（按产出表）：厨塔、神殿、酒吧、外卖、菜园、广场 NPC、嘻哈男孩、厨具。

**不模拟**（报告开头写明）：
- 好友互动、论坛、邮件、举报；
- 真人玩家抢菜；
- 厨具的强化过程；
- 区服里的蟹老板 NPC 店。

## 4. 架构

### 4.1 位置和入口

- 代码放在 `apps/server/src/sim/fast/`，属于服务端包，可以直接引用结算、规则和配置的代码。
- 不连数据库，不连 Redis。
- 命令 `pnpm sim:fast`：根目录和 `@dt/server` 各加一个脚本，在 `sim/cli.ts` 里加子命令 `fast`。

### 4.2 共用结算输入（先做的重构）

`settlement/runner.ts` 的 `settleOne` 现在是在函数内部从数据库行现场拼出 `SettleInput`。改法：

- 抽出一个纯函数 `toSettleInput(src: SettleSource): SettleInput`，放在 `settlement/globals.ts`；
- `SettleSource` 是拼输入需要的全部字段：店铺各列、桌子、食谱品级、食谱计数、加成汇总、特色菜、橱柜、当前时间；
- `settleOne` 改成先读数据库，组出 `SettleSource`，再调 `toSettleInput`；
- 快速模型从内存状态组出 `SettleSource`，调同一个函数。

两边拼出来的输入是同一段代码算的，不会跑偏。这次重构不改变结算行为，现有的结算测试必须全部通过。

### 4.3 内存状态

`FastRest` 对应真实店铺里会影响主线的字段：

- 店铺本身：等级、经验、银币、钻石、体力和体力上限、油和油壶、星级、餐桌上限、属性点、幸运、声望、街道、营业状态、自动做菜开关；
- 桌子 `TableState[]`，食谱品级 `Uint8Array`，食谱计数；
- 仓库：道具 id → 数量，带过期时间的单独存；
- 橱柜：食材 id → 数量；
- 设施格：已摆的设施；
- 加成来源：设施、勋章、产出表里的常驻加成，带过期时间；
- 当天计数：签到、任务进度、活跃度、免费合成次数等。

细节：
- **新店初值**用 `restaurant/rules.ts` 的 `newRestaurantValues` 和开店礼包，和真实开店一样。
- **加成汇总**用 `effects/aggregate.ts` 的 `aggregateEffects`，再加上收藏类派生加成（`collectionEffects`）。加成来源有变化、或者有加成到期时重算，其余时候用缓存。

### 4.4 一轮结算

每 4 分钟一轮：

1. 世界状态：
   - 天气按 `world/rules.ts` 的 `rollWeather` 在刷新时刻重掷；
   - 蟹老板巡街用 `rollKrabStreet`；
   - 节日倍率用 `config.holidayMultiplier`；
   - 痞老板按真实规则在一星以上、冷却已过的店里挑一家；
   - 小镇祝福先固定为空；
   - 最后用 `buildGlobals` 组出这一轮的全局参数。
2. 每家营业中的店：`toSettleInput` → `settleRestaurant`（游戏代码）。
3. 把结果写回内存，规则和 `settleOne` 一致：
   - 停业：标记为停业；
   - 正常：入账银币（最低到 0）；入账经验并处理升级（`applyExp`，加属性点、幸运、餐桌上限）；扣油；加声望；掉落进仓库；扣掉自动做菜用掉的食材；然后自动加油。
4. 体力恢复（`settlement/strength.ts` 的规则）。

### 4.5 机器人

- 画像、上线时间、每次上线的策略和 `sim/bot.ts` 一致：先签到，最后合成多余食材，顺序照搬。
- 每个动作都用游戏现有的规则函数判断：
  - 升星：`starChecks`；
  - 扩油壶：`oilChecks`；
  - 学食谱和升级食谱：`planLearn` 和 `applyLearn`；
  - 缺哪些食材：`foodsNeedFor`；
  - 合成：`runHandle`；
  - 菜场价格和限购：`unitPrice` 和 `personLimit`；
  - 任务进度：任务配置和 `task/rules.ts`。
- 机器人在内存里改自己的状态，不经过服务层。
- 规则函数做不到、要服务层才有的检查（例如商店的持有上限），在快速模型里各写一份最小实现，并在对应位置注释出处。

### 4.6 菜场

- 每个模拟区服一份货架，按 `tuning.market` 的上新时间用 `rollShelf` 上货；
- 库存、个人限购、价格按真实规则；
- 同一套数值里的机器人共用货架；
- 特价菜的同网络冷却不模拟，每个机器人当作不同网络；
- 竞猜按真实规则报名、开奖。

### 4.7 随机数

- 用种子派生出独立的随机源，各管各的：
  - 每家店的结算；
  - 每个机器人的操作；
  - 世界状态；
  - 菜场。
- 同样的参数跑两次，结果完全一样。
- 不同数值套用同一组种子，叫"公共随机数"：两套之间的差异来自数值，不来自运气。

## 5. 旁支产出表

### 5.1 文件

文件是 `apps/server/src/sim/fast/side-income.json`，跟着代码进仓库。命令行可以用 `--side <文件>` 换一张表。

```json
{
  "participation": { "diligent": 1, "normal": 0.7, "casual": 0.4 },
  "rows": [
    {
      "source": "town",
      "minLevel": 1,
      "coin": 0,
      "exp": 0,
      "diamond": 0,
      "strength": 0,
      "renown": 0,
      "goods": [{ "id": 1, "num": 3 }],
      "effects": {},
      "note": "雯姐每天送神秘礼券"
    }
  ]
}
```

- `source` 只能是 `town`、`hiphop`、`bar`、`yard`、`tower`、`temple`、`takeaway`、`equip` 之一。
- 数值字段都可以省略，默认 0。
- `goods` 的格式和奖励一致。
- `effects` 是常驻加成，键名和游戏的加成键一致，用来近似厨具、勋章对结算的影响。
- **等级段**：同一来源有多行时，取 `minLevel` 不超过当前等级的最高一行。
- **参与度**：实际获得 = 表里的数值 × 这个画像的参与度，银币、经验等数值和道具数量都向下取整，例如 3 个道具 × 0.4 = 1.2，取 1 个。常驻加成不打折。

### 5.2 发放

- 每个机器人每天第一次上线时，按当前等级发一次当天的旁支产出。
- 常驻加成按等级段替换：升到新的等级段时，换成新段的加成。
- 报告里按来源统计累计的银币、经验和钻石。

### 5.3 校验

加载时检查以下几项，有错直接报错并给出行号：
- 来源名是否合法；
- 道具 id 是否存在；
- 加成键是否是游戏认识的键；
- 参与度是否在 0~1 之间。

### 5.4 初值

初值由实现者按奖励表和 tuning 估算，每行在 `note` 写明依据，比如"每日次数 × 平均奖励"。用户之后可以直接改这个文件。

## 6. 命令和多套数值

```
pnpm sim:fast --days 30 --bots 20 --seed 1
  [--personas diligent,normal,casual]
  [--variant 名字=覆盖.json]...
  [--set tuning.路径=值1,值2,...]
  [--side 产出表.json] [--out 目录] [--stuck-days 5]
```

- **基准**：当前配置，总是一起跑，名字叫"基准"。
- **`--variant`**：可以写多个。覆盖文件的格式和区服覆盖一样，即 `{ "tuning": { ... } }`，深合并以后用 tuning 的 schema 校验，不通过就报错。
- **`--set`**：对一个 tuning 路径扫多个值，每个值算一套，名字就是 `路径=值`。一次只能写一个 `--set`。
- **数量上限**：基准加其他套最多 8 套，超过直接报错。
- **并行**：每套数值放在一个 `worker_threads` 线程里跑；线程数取 CPU 核数和套数的较小值。主线程只汇总结果、写报告。
- **进度**：每套每跑完 5 天打一行进度。

## 7. 报告

输出目录默认是 `sim-out/fast-<时间>/`，里面是 `report.html` 和每张表的 CSV。

`report.html` 是单个文件，图表用自绘的 SVG，可以复用 `sim/report.ts` 的 `lineChart`，再加上阴影带。内容依次是：

1. **说明**：这次跑的参数、套数、旁支产出表的路径，以及 §3 里"不模拟"的内容。
2. **关键指标对比表**：每套数值一行，按画像分栏，列出：
   - 到达 1、2、3……星的中位天数，括号里写到最后都没到的人占多少；
   - 第 7、14、30 天（不超过模拟天数）的中位等级；
   - 每天净银币的中位数；
   - 卡住的人占多少。

   和基准相差超过 10% 的格子，变好标绿，变差标红。
3. **曲线**：每种画像一组图，包括等级、星级、银币、学会的食谱数，横轴是天数。
   - 每套数值画一条中位数线；
   - 基准另外画出 10%~90% 的阴影带。
4. **旁支收入占比**：每种画像的银币、经验来自结算、旁支（按来源细分）、其他（任务、签到、掉落）各占多少。
5. **卡点**：等级够了却超过 `--stuck-days` 天升不了星的机器人占多少，按原因分类：
   - 缺某种食材（列出食材名）；
   - 缺银币；
   - 缺凭证；
   - 等级不够；
   - 其他条件。

## 8. 核对命令

`pnpm sim:fast --calibrate [--days 5] [--seed 1]`

- 同样的天数和种子，每种画像 1 个机器人，旁支产出关闭，两边各跑一遍：
  - 快速模型；
  - 现有全真模拟器，用一次性库 `dt_sim`，大约 2~3 分钟。
- 逐天比较每种画像的等级、星级、银币、学会的食谱数，打印对照表。
- 两边掷骰子的顺序不同，不要求完全相等。容差：
  - 等级差不超过 1；
  - 星级相同；
  - 银币差不超过 20%；
  - 食谱数差不超过 15%。

  超出的格子标红，最后打印"通过"或"不通过"，不通过时退出码为 1。
- 建议改了结算或成长规则以后跑一次。

## 9. 测试

- **结算输入一致**：在测试库造一家店（带设施、勋章、食谱），分别比较两份 `toSettleInput` 的结果，要求完全相等：
  - 真实结算器读库后组出 `SettleSource`；
  - 快速模型从等价的内存状态组出 `SettleSource`。
- **重构不改行为**：现有结算相关的测试全部通过。
- **一轮结算**：给定状态和种子，快速模型一轮之后的银币、经验、油、升级，和直接调用 `settleRestaurant` 再按 §4.4 第 3 步写回的结果一致；停业的店不入账。
- **机器人决策**：
  - 条件都够时会升星；
  - 只差凭证时买凭证；
  - 钱不够扩油壶时攒钱，不买菜；
  - 按缺口买菜，并留出一次加满油的钱；
  - 学菜优先学新的。
- **菜场**：上新时间、限购、库存被前面的机器人买光后，后面的买不到。
- **可复现**：同样的参数跑两次，结果完全相同。
- **公共随机数**：两套数值完全一样时，结果完全一样。
- **产出表**：参与度折算，等级段替换；来源名、道具 id、加成键写错时报错。
- **多套数值**：
  - `--set` 生成的套数和名字正确；
  - 覆盖不合法时报错；
  - 超过 8 套时报错。
- **冒烟测试，进 CI**：2 天、每种画像 2 个机器人、2 套数值，能跑通并写出 `report.html`。
- **速度**：30 天、每种画像 20 个机器人、1 套数值，在开发机上应在 30 秒内跑完。只在报告里打印用时，不作为 CI 断言；实现时如果超时，就在计划里加优化任务。

## 10. 文档

`docs/sim-fast.md`，写给要调数值的人，内容包括：
- 怎么跑；
- 怎么读报告；
- 怎么改产出表；
- 怎么做多套对比；
- 什么时候跑核对；
- 快速模型不模拟哪些内容。

## 11. 风险

- **快速模型的成长动作是重写的**：游戏规则改了要同步，否则两边会跑偏。缓解办法：
  - 尽量直接调用游戏的规则函数；
  - 结算输入由同一个函数生成；
  - 核对命令定期比较。
- **产出表是估算的**：报告单列旁支占比，避免它主导结论。
- **速度**：如果单线程跑 60 个机器人 30 天超过 30 秒，可以考虑的优化：
  - 机器人不在线时只结算不做别的；
  - 加成汇总缓存；
  - 减少对象分配。
