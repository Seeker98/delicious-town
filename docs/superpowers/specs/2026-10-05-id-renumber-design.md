# 道具、食材、菜谱重新编号 设计

- 日期：2026-10-05
- 来源：用户要求给道具重新编号（新旧道具的定义到处都是，编号完全乱），食材、菜谱一起考虑。
- 用户已定：
  - 道具按类别分段、段内按小类分块、留空位。
  - 食材、菜谱也重新编号；菜谱按街道分段，学会记录改用独立的“存储位”。
  - 线上（game.delicious.trade）玩家数据要保住：正式迁移。
  - 历史记录（餐厅日志、新闻、流水、结算掉落等）里的旧编号在迁移时一起改写。
- 不动：特色菜编号（1~335，基本连续）、天气、街道、设施（devices）等其他编号；道具图片（按名字取）。

## 1. 现状

### 1.1 编号

| 种类 | 数量 | 现在的编号 |
|---|---|---|
| 道具 | 715 | 1~642（原版，有空号，各类混在一起）；90001~90202 纪念品、抽赏券；91011~91124 一番赏月度手办；92014~92029 新街道勋章；93001~93208 食材随机券、基金勋章、后期海报奖杯 |

### 1.3 编号被用在哪

3. **数据库**：

   - 混合：`ledger`（`kind` + `item_id`，`source` 里有 `gift.<道具编号>` 这类）、`stat_daily.source`。

4. **外部**：Wiki 和开放接口的地址 `/wiki/goods/<编号>`、`/api/v1/open/{goods,foods,cookbooks}/<编号>`。

## 2. 编号规则

位数区分种类；新号段和所有旧号段不重叠，迁移后扫一遍旧号段就能确认有没有漏改。

### 2.1 道具：5 位，10000~89999

| 段 | 类别（goods.type） |
|---|---|
| 1xxxx | 消耗品、功能道具、残卷（0、1、8） |
| 2xxxx | 礼包（2） |
| 3xxxx | 设施（3） |
| 4xxxx | 厨具（4） |
| 5xxxx | 宝石（5） |
| 6xxxx | 荣誉（9） |
| 7xxxx | 纪念品、一番赏手办（10） |

- 段内再分**小类**，每个小类从整百开始（小类超过 100 件占两个百），小类内按旧编号的先后排，后面空着留给以后。
- 小类是主表里手工标的字段（`group`），不按 devicetype 自动分：消耗品、道具按 devicetype 会碎成 40 组。初步分法：
  - 1xxxx：货币和券、功能卡、神殿、菜园、特色菜、厨具强化、酒吧和小镇、其他；
  - 3xxxx：按摆放类型（牌匾、海报、奖杯、盆栽等）；
  - 4xxxx：按套装；
  - 5xxxx：按宝石种类；
  - 6xxxx：街道勋章（按街道顺序）、收藏类（盆栽、名画、雕像等各一块）、活动荣誉、工作证、基金勋章、其他；
  - 7xxxx：节日纪念品、一番赏手办（按月份）。
- 代码里按“基数 + 等级”算的编号，新方案里必须连续、等级顺序不变（生成脚本断言）：残卷碎片 1~6 级、N 级食材兑换券 1~5、一到五级食材随机券 1~5。
- 顺带消掉一个旧问题：现在蟹黄堡和“残卷碎片基数”都是 180。

### 2.2 食材：4 位，等级 × 1000 + 序号

- 1 级 1001 起……7 级 7001 起；万能食材 9001~9005，`FOODS.masterBase + 等级` 的算法照旧。
- 同等级内按旧编号的先后排。
- 编号一经分配就固定：以后改了某种食材的等级，编号不跟着改。

### 2.3 菜谱：6 位，100000 + 街道 × 1000 + 序号

- 例如 114023 = 14 号街第 23 道；同一条街内按旧编号的先后排（现在列表、学菜都按编号排，顺序不变）。
- 一条街超过 999 道才会不够（现在最多的 10 号街 333 道）。
- **存储位**：主表里每道菜一个 `slot`（从 0 起，只增不复用），学会记录的字节串按 `slot` 存，不再按编号。初始按新编号顺序给 0~3809，字节串从约 2 万字节缩到约 3800。删菜时它的 `slot` 空着不再用；加菜接在最大 `slot` 后面。

### 2.4 特色菜

编号 1~335 基本连续，这次不动。

## 3. 主表和数据归属

- 三份仓库自己维护的主表：`data/master/goods.json`、`data/master/foods.json`、`data/master/cookbooks.json`。
  - 每条带新编号、`legacyId`（旧编号）、道具的 `group`、菜谱的 `slot`，和现在构建要的全部字段。
  - 道具 7 份定义、食材 2 份、菜谱 2 份都收进来；`goods_awardflag` 补丁并进道具主表。
  - 一番赏、基金、新手礼包等文件里除定义以外的内容（主题、档位、礼包内容）留在原文件，只改成引用主表编号。
- `sync-data` 不再同步道具、食材（菜谱已经不同步）；`goods_sources.json` 仍按旧编号保留（原版资料），工具通过 `legacyId` 对上。
- `import-new-streets`：外部数据的编号是新街道菜谱、食材、勋章的旧编号。导入时按主表的 `legacyId` 换成新编号；外部新出现的条目按规则分配新编号、写进主表。那边不用改。
- 构建产出的配置包带三张“旧 → 新”对照（只用于下面第 5 节的旧链接跳转和工具显示原版途径）。

## 4. 代码

- 常量全部换成新编号；“基数 + 等级”的常量换新基数。
- 测试里写死的编号先换成常量或按名字查（第 6 节 PR 2），重新编号那次就只改常量和数据。
- 前端只依赖 `SHARED_GOODS` 和后端下发的数据；`StoreView` 的 87 改成常量。
- 学会记录：`padLevels`、读写都按 `slot`；`cookbookIndex` 提供 编号 ↔ `slot`。

## 5. 旧编号兼容

- Wiki 的 `/wiki/goods/<旧编号>`、`/wiki/foods/…`、`/wiki/cookbooks/…` 和开放接口的详情接口：编号落在旧号段时，按对照表跳到新编号（旧号段和新号段不重叠，不会认错）。
- 列表接口直接是新编号。
- 对照表永久保留。

## 6. 分四个 PR

### PR 1：主表整合（编号不变）

- 建三份主表，编号先保持旧的（`legacyId` 先等于编号），并标好道具 `group`、菜谱 `slot`（先等于编号）。
- 构建改为从主表读；删掉被合并的旧定义文件；`sync-data` 停同步道具、食材。
- **验收**：构建产出的配置包和改动前逐字节相同（版本号不变）。

### PR 2：去掉写死的编号（行为不变）

- 代码、测试里的编号字面量换成常量、按名字或按条件查。
- 加一条检查：服务端源码（除常量文件）不再出现道具、食材、菜谱编号字面量（规则写成测试，扫描源码）。
- **验收**：全部测试通过，配置包不变。

### PR 3：菜谱存储位（行为不变）

- 学会记录按 `slot` 读写；`slot` 此时等于编号，库里数据不用动。
- **验收**：全部测试通过；加测试：`slot` 和编号不同时，读写、补齐、学菜、计数都对。

### PR 4：重新编号和数据迁移（一起上线）

1. **生成对照表**：脚本按第 2 节规则从主表生成新编号，输出：
   - 三张对照表；
   - 一份审阅报告（每个小类的起止编号、每件道具新旧编号），先给用户审，确认后再继续。
2. **改写配置**：主表、所有引用、翻译键、区服数值默认值、常量换成新编号；菜谱 `slot` 按新编号顺序重排。
   - 同一份对照表脚本也改写测试数据（PR 2 审查发现，不在 PR 2 手改）：模拟器输入 `apps/server/src/sim/fast/side-income.json`、`apps/server/src/sim/examples/*.json`；e2e 脚本 `apps/web/e2e/*.spec.ts` 里 SQL 插入的编号、接口参数和带编号的选择器（如 `buy-310`、`basket-store-101`、`selectOption('165')`）。
   - PR 2 之后测试里仍可能有扫描规则看不到的零星编号（编号数组、报错文字等，已按审查清单改掉大部分）；换号后跑全量测试，失败的逐个改成常量或按名字查。
3. **数据迁移**（一个迁移、一个事务）：
   - 对照表冻结一份放进迁移目录（以后主表再改也不影响这次迁移）。
   - 普通列：建临时对照表，`update … from` 一次改完。
   - 学会记录：每家店的字节串按“旧编号 → 新 slot”重排。
   - JSON 列和带编号的文本（`ledger.source`、计数键）：按已知结构改写，分批处理。日志、新闻按类型逐个列出参数里哪些是编号（以代码里写日志、新闻的地方为准，写成表，迁移和测试共用）；奖励结构（`goods` / `foods` 数组、`{ kind, id }`）通用处理。
   - 迁移结束前自检：各表、各 JSON 里不再有落在旧号段的编号；道具、食材的持有总数，学会菜谱数，与迁移前相同。不通过就回滚整个事务。
4. **演练**：在开发库的完整副本上跑迁移，核对第 3 步的数字，记下耗时，用来安排线上停服时间。
5. **上线**：停服 → 备份 → 迁移 → 启动。迁移不提供回退，出问题从备份恢复。
- **验收**：演练通过；全部测试通过；Wiki 旧链接跳转正确；游戏里随机抽查仓库、橱柜、学会的菜、邮件、活动、日志显示正常。

## 7. 风险

- **漏改某处编号**：旧号段不重叠 + 迁移自检 + PR 2 的源码扫描，三道拦截。
- **日志参数结构没列全**：老日志显示错名字（不影响数值）。自检扫旧号段时能发现，演练阶段补全。
- **线上数据量比开发库大**：演练时按开发库耗时估算，迁移分批写，事务时间过长时改成按表分段提交（每段幂等：旧号段已改过的跳过）。
- **新街道外部数据**：导入按 `legacyId` 对照，外部改编号的检查照旧（`--allow-removed`）。
- **区服数值覆盖**：按区服存的覆盖里的编号随迁移改写；后台在迁移后只认新编号。
