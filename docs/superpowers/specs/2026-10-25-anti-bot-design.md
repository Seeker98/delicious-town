# 游戏接口防脚本：请求签名、节奏标记（设计）

日期：2026-10-25。延续 PR #340（开放接口调用记录）。

## 为什么做

用户定的原则：**玩家可以随便拿数据算策略（开放接口、外部工具都行），但游戏里的每个操作必须是真人在我们的网页里点出来的。**

担心的情况是有人不开网页、直接写程序调游戏接口把整个游戏挂着跑。10-24、10-25 的只读排查已经看到苗头（店 41、44 一周手动加油几百次、半夜照加；逍遥山庄在豆包里做了调开放接口的应用），但游戏接口只记了登录痕迹，认不出“程序调用”和“网页点击”。

## 目标

1. **第一道门（自动拦）**：写操作必须带只有我们网页才会生成的签名；签名缺失、过期、重放、对不上、或者浏览器暴露“被自动化工具控制”的，**这一下操作失败**，不处罚账号。
2. **第二道门（后台标记）**：按账号统计操作节奏，在后台“可疑数据”里标出像机器的账号，由用户判断、手动处理。
3. 让“把浏览器里的请求复制下来重放”失效，让“自己实现签名”的成本尽量高。

## 不做什么

- **不按点击快慢拦截。** 游戏里很多操作本来就要连点（一次学很多菜、处理食材、一键操作），频率只用于标记，不用于拦。
- **不做“操作前必须先进对应页面”的拦截**（用户 10-25 定）：238 个写接口要逐个对应页面，工作量大；通用版脚本一行就能绕过，又会误伤停在学菜页一直点的真人。改成节奏统计里的一个参考项（见下）。
- **不自动封号、不自动加人机验证。** 处罚都由用户在后台手动做。
- 不管开放接口（`/api/v1/open/*`，只读静态资料，本来就允许外部调用）。
- 不追求“无法破解”：网页代码跑在玩家浏览器里，能算出签名的东西有心人一定能照抄。目标是抬高成本、让复制失效，再靠节奏标记兜底。

## 失败的样子（反目标）

- 正常玩家在网页里操作被拦（尤其是：刚发版、页面还开着旧版本；多个标签页；手机应用内嵌浏览器；网络慢导致时间戳偏差）。
- 每个请求多出明显的延迟或数据库写入压力（服务器配置不高）。
- 后台标记出一大堆真人，没法用。

## 上线方式（用户定）

**先只记录、不拦**：区服设置加一个开关，默认“只记录”。过一次发版、旧页面都刷新过、后台看确认没误伤后，用户在后台把开关改成“拦截”。

## 设计

### 1. 请求签名（写操作）

只签写请求（`POST`）。读请求不签，只带版本号（见 2）。

- **签名密钥**：每个登录会话一把随机密钥，存在 Redis 里现有的会话数据（`SessionData`）里。网页在拿到登录状态后向服务器取一次（只在带会话 Cookie 的请求里返回；不写进 Cookie、不落库）。会话重建（登录、被挤掉）时换新密钥。老会话没有密钥时，取的时候补一把。
- **一次性随机数**：直接用现在每个写请求都带的 `idempotency-key`（网页每次生成新的 UUID）。必须参与签名，所以改了它就得重签。
- **时间戳**：网页用已有的服务器时钟校准（`utils/serverClock.ts`）取当前毫秒数。服务器只接受前后 2 分钟内的（具体窗口builder定，要容得下手机网络慢）。
- **签名内容**：时间戳、随机数、方法、路径（不含域名，含查询串）、请求体的 SHA-256、前端版本号、环境检查结果，按固定顺序拼起来，用 HMAC-SHA256 签。网页用浏览器自带的 WebCrypto 算。
- **防重放**：服务器校验通过后，把“账号 + 随机数”在 Redis 里记 2 个窗口长的时间（`SET NX EX`），再出现就拒绝。注意和现有的防重复提交（`security/idempotency.ts`）的关系：同一个 key 的合法重试目前会拿到缓存响应，这个行为要保留——签名校验放在防重复提交**之后**，或者对“防重复提交命中缓存”的请求跳过重放检查，builder 选一种并写测试。
- **哪些请求要校验**：带登录会话的写请求。没登录的（注册、登录、找回密码）不签，那些已经有人机验证。后台（`/api/v1/admin/*`）也要签——管理员账号同样走网页。测试接口（`/api/v1/test/*`）不签。

### 2. 前端版本号和环境检查

- **版本号**：构建时注入（git 提交号或构建时间），每个带会话的请求（读写都带）放在请求头里。服务器只校验格式并记录，不维护“有效版本列表”（网页和接口不一定同时部署）。缺失版本号算“非网页请求”。
- **环境检查**：网页启动时算一次，写成一个小整数（位标记）放进签名。至少包括：`navigator.webdriver` 为真、浏览器标识里有 `HeadlessChrome`。其他检查项 builder 可以加，但**只有这两项在拦截模式下直接拒绝**，其余只记录（避免误伤各种手机内嵌浏览器）。
- **最近一次真人操作**（用户 10-25 定：页面内脚本先记录、只标不拦）：签名只能证明“请求是我们网页的代码发的”，挡不住在我们页面里挂的油猴脚本、自动点击插件。网页全局监听点击、触摸、按键，只认浏览器标记为真人触发的事件（`isTrusted`），记下最近一次的时间；每个写请求把“距离最近一次真人操作过了多少毫秒”写进签名。服务器**不据此拦截**，只计入节奏统计（见 4）。没有点击也会自动发的写请求（比如公告已读）、一次点击连发多个请求的批量操作会让这个数偏大，所以只用作参考，不单独定罪。

### 3. 校验结果和拦截

服务器对每个要校验的写请求得出一个结果：通过 / 没签名 / 过期 / 重放 / 签名不对 / 自动化环境 / 没版本号。

- **只记录模式**（默认）：请求照常执行，结果计入节奏统计。
- **拦截模式**：除“通过”外一律拒绝，返回新的错误码，网页提示“请在游戏网页里操作；如果你是在网页里点的，请刷新页面”（5 种语言）。不扣东西、不处罚账号。
- 开关放在区服设置（`tuning`，后台可改，有历史）。会话还没选区服的写请求（选区服本身等）按只记录处理。
- **后台接口永远只记录、不拦**（我的决定，审阅时提出）：开关本身是在后台改的，万一某次发版把签名弄坏（比如混淆出错），拦截模式下连“改回只记录”都会被拒，后台把自己锁在外面。
- **服务器环境变量总开关**（我的决定）：加一个环境变量，设了就强制“只记录”，优先于区服设置。签名出事时改环境变量、重启 api 就能恢复，不依赖后台能不能用。
- 开发区服、e2e 测试保持“只记录”（现有 e2e 用 Playwright，`navigator.webdriver` 为真，也有直接发写请求的用例）。

### 4. 节奏统计（后台标记用）

在请求钩子里用 Redis 计数，**不在请求里写数据库**；定时任务每小时把上一小时的计数汇总写进一张新表，保留 30 天（和 `login_trace`、`open_trace` 一样由清理任务删）。按“账号 × 小时”一行，至少包括：

- 写请求数、读请求数
- 各路由的写请求次数（JSON，只记写请求）
- 相邻两次写请求的间隔：次数、总和、平方和、最小值（用来算间隔是不是规律得像钟表）
- 写请求前 5 分钟内没有任何读请求的次数（不拦，只做参考；见“不做什么”）
- 写请求时距离最近一次真人操作超过 1 分钟的次数（具体阈值 builder 定；见 2“最近一次真人操作”）
- 签名校验各种结果的次数
- 这一小时出现过几种浏览器标识、几个设备号、几个 IP

### 5. 后台“操作节奏”标签页

放在后台“可疑数据”里，和现有“接口调用”等标签页并列。按账号列最近 7 天：

- 每天有操作的小时数（24 小时里几小时）、最长连续有操作的小时数、凌晨 2~7 点的操作数
- 写请求总数、间隔的规律程度（变异系数之类，builder 定具体算法，要能把“学菜时一阵猛点”和“全天匀速”分开）
- 写操作前没看页面的次数、写操作前很久没有真人操作的次数
- 签名校验不通过的次数（按原因）
- 关联的店名、账号名，能跳到现有的多号、封禁功能

默认按“最像机器”排序；排序打分 builder 定，但**规则要写在页面上**，让用户知道为什么排在前面。

**账号白名单**（用户 10-25 定）：同一个标签页里可以把账号加进白名单、移出白名单（写审计日志）。白名单里的账号**拦截模式下也不拦**，照样记录；在节奏列表里标“白名单”、排到最后。用途是用户自己的号、帮用户干活的 AI 工具（可能用带自动化标记的浏览器）。上线时名单为空；账号 2「Seeker」是不是用户自己的号还没确认，不默认加。

### 6. 可疑号人机验证（后手，手动）

后台对某个账号打开“需要人机验证”（带到期时间）。打开后这个账号的写请求每隔一段时间（比如 1 小时，builder 定，做成设置）要带一次 Cloudflare 人机验证结果；没有就返回专门的错误码，网页弹出人机验证框（复用注册页的 `TurnstileBox`），通过后自动重试刚才那个操作。服务器校验复用 `infra/captcha.ts`。

### 7. 签名代码混淆（加成本）

签名那一个模块在构建时单独混淆，每次构建结果不同。只混淆这一个小文件，不影响其余代码的报错定位。**放在最后做**；如果引入的依赖、构建时间或包体积代价明显，builder 回来报告，可以不做。

## 约束

- 服务端：Fastify 钩子统一处理（参考 `security/idempotency.ts`、`modules/account/loginTrace.ts` 的 `registerPlayTrace`）；Redis 计数不阻塞请求、失败只记日志，和 `registerPlayTrace` 一样。
- 网页：只改 `apps/web/src/api/client.ts` 这一个出口加签名和请求头；其余页面不用动（人机验证弹框除外）。
- 现有服务端测试大多直接调服务层，用 `inject` 的只有少数几个；默认“只记录”模式下它们不受影响。拦截模式要有专门测试。
- 每个 PR 写一条玩家可见的更新记录（5 种语言）——这次玩家可见的只有新的错误提示，builder 判断要不要写。
- 迁移：新表两张（节奏统计、账号白名单）；会话数据存在 Redis，不用迁移。

## 交给 builder 决定的

- 时间窗口长度、Redis 键的结构和过期时间、汇总任务的具体时间。
- 环境检查除了两项硬性的以外还检查什么。
- 节奏统计的“像机器”打分规则（写在后台页面上）。
- 混淆用什么工具，或者评估后不做。
- PR 怎么拆：建议先做 1~5（签名 + 版本号 + 节奏统计 + 后台页面），6、7 另开。拆的时候注意别做叠起来的 PR（用户会连着合）。
