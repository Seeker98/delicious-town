# 随机事件和问答（设计稿 2026-10-28）

内容样例: `analysis/随机事件样例-2026-10-28.md`（150 个事件、97 道问答，下称“样例”）。本稿只讲机制，事件和题目的文字、效果都以样例为准。

## 1. 要做什么、为什么

玩家在线时，店里隔一阵子会冒出一件“莫名其妙的小事”：有的直接给一个短时的加成或减益，有的让玩家二选一，有的是一道问答，答对了给道具。目的是让每天上线多一点意外和话题，不是新的收益来源。

**用户已定的（2026-10-28）**
- 事件取材于欧洲生活，另有一批英伦风，但文字里不出现国名、地名，不让人一眼看出原型（问答是现实知识，可以写国名）
- 量要够玩十天半个月：样例的 150 个事件、97 道问答
- 题库不分语言：只适合简中的网络流行语题已经删掉，所有题翻译后五种语言通用
- 现实题标“写于哪年”（现在都是 2026），AI 和 meme 题每年复查
- 样例里的内容、效果方向都过目了

**不做的**
- 不做排行、不做全服统计（“多少人选了 A”留到以后）
- 不给钻石、不给高价值道具；奖励只有银币、经验、食材、神秘礼券
- 不做新的加成玩法：效果只用结算、外卖、灭蟑螂、特色菜里已经在读的加成键（第 5.1 节）
- 后台不做事件编辑器：事件和题目在配置数据里，加内容走 PR

## 2. 概念

| 名词 | 意思 |
|---|---|
| 事件 | 配置里的一条，编号 1 起，和样例的编号一致 |
| 题目 | 配置里的一条，编号 1 起，和事件分开编号 |
| 通知 | 事件的一种：弹出即生效，只有“知道了” |
| 选择 | 事件的一种：2~3 个选项，选了才生效；结果可以带随机 |
| 问答 | 一道题。知识题有对错；选择题没有对错，每个答案给不同效果 |
| 问答夜 | 样例第 40 条：一次连出三道知识题，按答对几道给奖励 |
| 时段 | 一个游戏日按 4 小时切成 6 段，每段最多出一件（事件或问答） |
| 一次出现 | 某家店在某个时段抽到的那一件，存一行（第 8 节） |

## 3. 节奏

- **按时段抽**：玩家在线、前端来问“现在有没有事件”时（第 9 节），服务端看这一时段抽过没有，没抽过就抽一次并记下来。同一时段刷新多少次都不会重抽。
- **每段必出一件**：问答占三分之一，事件占三分之二。一个人每天在线覆盖 6 段的话，就是 4 个事件 + 2 道题；平常玩家覆盖 3~4 段，就是两三件。0~4 点那段一般碰不到，正好。
- **没处理完不抽新的**：上一件“选择”或“问答”还没回答，就不抽新的。挂着的超过 4 小时作废（不给效果，也不扣东西）。
- **不重复**：同一个事件 7 天内不再出；知识题答过就不再出（全答完以后从最早答过的开始重出）；没有对错的选择题 14 天内不再出。没答就作废的题不算出过（2026-10-31）。
- **新手**：店铺等级不到 10 级的，不出带减益的事件（有没有减益由构建时按效果算出），免得第一天就被扣上座率。

### 3.1 抽法

1. 筛出“现在能出”的事件或题目：满足出现条件（第 6 节），不在不重复期内
2. 先按 `quizShare`（1/3）决定这一次出问答还是事件
3. 加权随机：普通 10，稀有 1（样例第 126~131 条）；连续剧的下一段 10，每多等一天 +5，最多 40
4. 问答夜（第 40 条）也是一个事件，抽中后从知识题里再抽三道

随机数用 `op.rng`，和其他玩法一样。

## 4. 数据格式

`packages/config/data/designed/random_events.json`（简中文字）+ `data/i18n/{en,es,fr}/random_events.json`（翻译）；繁中照例构建时转换。Zod 模式写在 `packages/config/src/randomEvents.ts`，构建进配置包。题目同理，用 `random_quiz.json`。

事件：

```jsonc
{
  "id": 3,
  "kind": "choice",                 // notice | choice | quizNight
  "title": "进门须知",
  "body": "镇上出了新规定: 客人进门前要先读一份《用餐偏好说明》, 逐项勾选同意。你打算怎么排版?",
  "weight": 10,                     // 可省略，默认 10；稀有写 1
  "when": { "hours": [13, 17], "weekdays": [7], "months": [12], "dates": ["11-01", "11-10"], "weather": [1, 28], "minLevel": 1 },
  "after": { "events": [111], "option": "a", "minDays": 1 },   // 连续剧的前置：做过其中任意一个，可省略；选择事件没选、问答夜一道没答就作废的不算做过（2026-10-31）
  "options": [
    {
      "key": "a",
      "label": "把“全部同意”做成大大的按钮",
      "cost": { "coinPerLevel": 0 },
      "outcomes": [
        { "weight": 1, "text": "客人进得快, 可发现被推荐了一堆不想吃的菜。", "effects": { "atRate": 0.04, "spRate": 0.1 }, "hours": 2 }
      ]
    }
  ]
}
```

- `notice` 没有 `options`，直接写一个 `outcome`
- 一个选项有多个 `outcomes` 时按 `weight` 随机（样例第 5、16、35、44、81、100、107 条）
- 歌唱大赛（第 5 条）、商会会长选举（第 125 条；小镇已有镇长大胃锅，样例改成商会）这种“押中没押中”，写成选项下两个结果，权重 1:2 或 1:1
- `when` 各项都可省略；`hours` 是游戏时间左闭右开；`dates` 是月-日的起止

题目：

```jsonc
{ "id": 20, "type": "fact", "year": 2026, "recheck": false,
  "q": "2025 年, 北大毕业的数学家王虹和合作者证明了三维的“挂谷猜想”。这个猜想最早来自哪个问题?",
  "choices": ["一根针在平面上掉个头, 最少要扫过多大面积", "地图最少要几种颜色才能把相邻的国家分开", "橙子怎么堆最省地方", "一张纸最多能对折几次"],
  "answer": 0,
  "explain": "其他三个也都是有名的数学问题。挂谷问的是转针: 答案是面积可以想多小就多小。",
  "reward": { "tickets": 1 } }
```

- `type`: `game`（游戏知识）、`fact`（现实知识）、`opinion`（没有对错）
- `game` 和 `fact` 有 `answer`；`opinion` 没有，每个选项各带 `effects` / `hours` / `reward`
- `year`、`recheck` 只有现实题写；构建时检查 `fact` 都有 `year`
- 第 6 题“品级最高”是特例：`"dynamic": "grade"`，选项在服务端从品级表里抽

## 5. 效果和奖励

### 5.1 加成

挂到现有的 `effect_source`：`sourceType: 'randomEvent'`，`sourceId` = 事件编号（问答的选择题用 1000 + 题号），`expiresAt` = 现在 + 时长。同一个事件再出现是覆盖，不会叠加；不同事件之间直接相加，和天气、宿醉一样。

允许的键（构建时检查，不在表里的报错）：

| 键 | 读它的地方 |
|---|---|
| `atRate` `spRate` `coinRate` `expRate` `coinValue` `expValue` `oilRate` | 结算 |
| `luckValue` | 幸运（全部玩法） |
| `mcGoldRate` | 烹制特色菜 |
| `killRoachNoStrengthRate` | 灭蟑螂 |
| `taNeedtimeRate` `taCoinRate` `taExpRate` `taSuccessoddsRate` | 外卖 |

范围（构建时检查）：比率类 ±0.15 以内（外卖的四个键 ±0.3，天气里本来就到 ±60%），`atRate` 的减益不低于 -0.05；`expValue`、`coinValue` ±2 以内；幸运 ±30；时长 1~12 小时。带不带减益由构建时算出，数据里不用标 `debuff`。

**样例里标了 [需接] 的 4 条，第一版不接，改成现有的键**（其他模块要读加成汇总，改动面大，划不来）：

| 样例 | 原来 | 改成 |
|---|---|---|
| 1 装卸队去散步 | 菜价 +15%、上座率 +6% | 只留上座率 +6%；正文去掉“菜价涨了一点” |
| 14 广场的鸽子 | 导弹命中 -10% | 上座率 -3%，正文改成“鸽子在门口抢面包屑, 客人绕着走” |
| 29 打折季 | 菜价 -15% | 上座率 +5%，正文改成“逛街的人多了” |
| 143 摊主拌嘴 | 菜价 -10% | 随机食材 ×2，正文加“摊主吵完塞给你一把” |

**幸运的量级**：样例里写“少量”的 = `luckValue` +10，“中等”的 = +30。幸运率是 √(3 × 幸运) / 100，一家 50 级的店基础幸运约 50（12.2%），+10 变成 13.4%，+30 变成 15.5%。

### 5.2 奖励

```jsonc
"reward": { "coinPerLevel": 20, "expPerLevel": 5, "tickets": 1, "foods": { "num": 3 }, "goods": [{ "id": 0, "num": 1 }] }
```

- 银币、经验按店铺等级乘，走 `grantAward`（`source: 'event.<编号>'`）
- `tickets` 是神秘礼券（`GOODS.mysteryTicket`）
- `foods` 是“随机食材 ×N”：和礼包里“按等级给食材”同一个抽法（带缺料倾向），食材等级取这家店当前能做的最高菜谱的食材等级，实现时看菜谱等级规则定
- 第 27 条“随机 1 级食材”写 `"foods": { "num": 10, "level": 1 }`
- `goods` 留着备用，第一版内容不用

### 5.3 花钱的选项

`cost.coinPerLevel`（第 16、27、47、70、81、114 条）：选的时候扣银币，银币不够时这个选项置灰，旁边写价格。

## 6. 出现条件

| 条件 | 用在 |
|---|---|
| `hours` 游戏时间 | 早上、中午、傍晚、夜间、深夜的事件 |
| `weekdays` 星期几 (1~7) | 周日安静、周五炸鱼、周四问答夜等 |
| `months` 月份 | 季节：冬季 12~2、春季 3~5、夏季 6~8、秋季 9~11，按现实月份，不和时令挂钩 |
| `dates` 月-日 | 篝火之夜 11-01~11-10、纸皇冠 12-20~12-31、元旦冰海 01-01 |
| `weather` 天气编号 | 天气联动；取区服当前生效的天气（含自选天气覆盖），即 `world.ensure(...).weather` |
| `minLevel` | 默认 1 |
| `after` 前置 | 连续剧、第 94 条新邻居 |

第 150 条“雨后放晴”第一版简化成“只在晴天出现”，不判断上一个天气。

## 7. 问答

- **答案不进前端目录**：目录里只有题面和选项。服务端在出题时打乱选项顺序并存下来，玩家答完，接口才返回正确的是哪个和解说。
- **只能答一次**，答完不能改。
- **奖励**：知识题答对按题目的 `reward`（默认神秘礼券 ×1）；答错给经验（等级 × 5），附解说。选择题按所选答案给效果或奖励。
- **问答夜**：一次出三道，逐题回答，每道答完立刻告诉对错；三道都答完按答对数发奖（3 道 → 礼券 ×3，1~2 道 → 礼券 ×1，全错 → `expRate` +3% 1 小时）。中途关掉窗口，下次打开从没答的那题继续。超时作废时已答对的按比例算。
- **动态题**（第 6 题）：服务端从“普通”到品级上限（`tuning.rest.cookbookMaxGrade`，现在是佳肴）里随机抽四个，答案是其中最高的那个；前端按 `labels.grade` 显示名字。

## 8. 存储

迁移 `0099_random_events`，一张表：

```sql
create table random_event (
  id          bigserial primary key,
  rest_id     integer not null references restaurant(id) on delete cascade,
  slot        text not null,              -- '2026-10-28#3'：游戏日 + 时段序号
  kind        text not null,              -- notice | choice | quiz | quizNight
  ref_id      integer not null,           -- 事件编号或题号
  quiz_ids    integer[],                  -- 问答夜的三道题
  status      text not null,              -- pending | done | expired
  choice      text,                       -- 选项 key，或题目答的选项下标（打乱前）
  outcome     jsonb,                      -- 实际给了什么：结果下标、效果、奖励、答对几道
  payload     jsonb,                      -- 选项顺序、问答夜进度等
  seen        boolean not null default false,
  created_at  timestamptz not null,
  expires_at  timestamptz not null,
  resolved_at timestamptz,
  unique (rest_id, slot)
);
create index random_event_rest_time on random_event (rest_id, created_at desc);
```

- 通知类在抽中时就生效，`status` 直接是 `done`，`seen` 等玩家点“知道了”才置真
- 不重复、连续剧前置都查这张表
- 每日清理任务删 180 天前的行（知识题“答过不再出”因此最多管 180 天，够了）

## 9. 接口

| 接口 | 做什么 |
|---|---|
| `GET /api/v1/random-events/current` | 在 `runOp`（锁店铺行）里：作废超时的；当前时段没抽过就抽；返回要给玩家看的那一件（挂着的选择或问答，或没看过的通知），没有就返回空 |
| `POST /api/v1/random-events/:id/choose` `{ option }` | 选择事件：扣花费、按权重抽结果、挂加成、发奖励，返回结果 |
| `POST /api/v1/random-events/:id/answer` `{ index, q? }` | 问答和问答夜：判对错、发奖，返回正确选项和解说（按请求的语言） |
| `POST /api/v1/random-events/:id/seen` | 通知点了“知道了” |

- 都带 `?lang=`，文字按语言给（配置包的翻译，没翻的用简中）
- 功能开关 `randomEvents`（第 11 节），关掉时 `current` 返回空，其他接口报功能未开放
- 回答时发现已超时：报 `random_event_expired`，这次操作整体回滚，作废留给下一次 `current`
- 每次了结记 `restLog('randomEvent')`（店铺日志里显示一句），并发 `emitAction('randomEvent.done')`，以后要做成就时直接能用
- 防脚本：带登录会话的写请求自动校验签名（只跳过开放、测试接口），新接口不用另外登记

## 10. 前端

- **弹窗** `components/RandomEventPopup.vue`，和 `AnnouncePopup` 一样挂在 `App.vue` 里（`inGame` 时）；模板里排在公告前面，同时有时公告盖在上面
- **什么时候去问**：进游戏、回到首页、页面从后台切回前台时各问一次，开着的时候每 10 分钟问一次
- **卡片**：标题、正文、选项按钮（花钱的写价格，钱不够置灰）；选完原地换成结果文字 + 效果标签（“上座率 +6% · 2 小时”）+ 奖励
- **问答卡片**：题面 + 四个选项；答完标出对错和解说；问答夜顶上显示“第 2 / 3 题”
- **文字由接口给**（实现时改的，原来打算放进目录）：目录已经约 290KB，事件和题目的全文不放进去；接口按 `?lang=` 给这一件的文字，题目答完才给正确答案和解说。目录只在 `data.randomEvents` 里放事件标题，首页“生效中的加成”按 id 取名字
- **生效中的加成**：归在“其他”分组，名字取事件标题；`utils/serverText.ts` 的 `effectName` 加 `case 'randomEvent'`，没有对错的问答（`sourceId` ≥ 1000）显示“小镇问答”；服务端 `effects/naming.ts` 同样加一行
- **效果标签的名字**：`util.effects` 补上 `killRoachNoStrengthRate` 和 4 个外卖键，五种语言；奖励的“名字×数量”用 `common.qty`

## 11. 区服设置和数值表

- 功能开关 `randomEvents`：加进 `IMPLEMENTED_FEATURES` 和 `DEFAULT_OFF_FEATURES`，上线后在后台逐个区打开（同小镇日报）
- `tuning.randomEvents`（区服可覆盖，`settingDocs` 写说明）：

| 键 | 默认 | 说明 |
|---|---|---|
| `slotHours` | 4 | 时段长度，必须能整除 24 |
| `quizShare` | 0.33 | 一次出问答的概率 |
| `pendingHours` | 4 | 挂着多久作废 |
| `noRepeatDays` | 7 | 事件不重复天数 |
| `opinionNoRepeatDays` | 14 | 选择题不重复天数 |
| `chainWeightPerDay` / `chainWeightMax` | 5 / 40 | 连续剧下一段每等一天加的权重、上限 |
| `newbieLevel` | 10 | 低于这个等级不出带减益的事件 |
| `correctTickets` | 1 | 知识题答对默认给几张神秘礼券（题目自己写了奖励的按题目） |
| `wrongExpPerLevel` | 5 | 答错的安慰经验：等级 × 这个数 |
| `foodLevelStep` / `foodLevelMax` | 10 / 4 | “随机食材”没写等级时：店铺每 10 级食材等级加 1，最高 4 级 |
| `retainDays` | 180 | 记录保留天数 |

幸运直接在数据里写数值：样例的“少量”写 10，“中等”写 30。

## 12. 数值总量

- **加成**：每段一件、效果大多 1~3 小时，同一时间平均约 1 个事件在生效。样例里增益多、减益少且小，粗算对营业收益的平均影响在 +2% 左右。上线前用快速模型（`sim-fast`）各跑一遍“只开增益”和“全部效果”核对，超过 +3% 就整体调低。
- **神秘礼券**：样例里给礼券的结果按权重粗算：每件事件期望约 0.2 张；知识题答对给 1 张、答对率按七成算，每道题约 0.5 张。活跃玩家每天约 2 张。按礼券核算的口径（1 张 ≈ 1,200 银币）约 2,400 银币，但礼券拿去酒吧会放大，上线前对着 `酒吧礼券调整核算-2026-10-26.md` 再算一次。
- **银币、食材**：按等级给，数额小（每次约是一轮营业的零头），不单独核算。

## 13. 文案和翻译

- 简中按规范写：“: ”“, ”、半角括号（`build.test` 会挡全角的）
- 英、法、西的翻译和内容一起进 PR，法文百分号前的窄空格写成 `\u202f` 转义
- 现实题翻译时只译不改；英伦题在英文里照样成立
- 繁中最后跑 `i18n:tw` 生成，不手改、不格式化
- 更新记录一条，五种语言

## 14. 测试

- **配置**：每个事件、题目的格式；效果键在允许表里、数值在范围内；`fact` 题都有 `year`；`after` 指向存在的事件和选项；编号不重复；游戏知识题的答案和现在的天气数据一致（天气改了测试会失败，2026-10-28 样例里出现过已删掉的卖艺男孩）
- **服务端**：
  - 同一时段多次请求只抽一次
