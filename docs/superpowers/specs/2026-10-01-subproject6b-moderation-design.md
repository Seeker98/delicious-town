# 子项目 6B：举报和审核、可疑数据、区服数值说明、上线检查 设计

日期：2026-10-01
状态：待用户审阅

## 1. 范围和拆分

子项目 6 的第二轮，负责"管东西"。6A 做的是"发东西"（邮箱、公告、兑换码、邀请）。分两个 PR：

| PR | 内容 |
|---|---|
| 6B-1 | 举报和处理（§3）；封号期限（§4）；问题记录 164~170 小改（§8） |
| 6B-2 | 可疑数据页（§5）；区服数值说明，即问题记录 126（§6）；上线检查（§7） |

设计文档只有这一份，实现计划按 PR 各写一份。

**不在本次范围**：
- 敏感词过滤；
- 自动处罚；
- 举报人的信誉分。

## 3. 举报和处理（6B-1）

### 3.1 数据（迁移 0019）

**`report_case`**：一个被举报的内容一个案子。

| 列 | 说明 |
|---|---|
| `id` | 主键 |
| `shard_id` | 区服 |
| `target_type` | `post` / `reply` / `broadcast` / `rest_name` / `notice` |
| `target_id` | 帖子 id / 回复 id / 新闻 id / 餐厅 id / 餐厅 id |
| `target_rest_id` | 被举报的店 |
| `target_account_id` | 被举报的账号 |
| `snapshot` | 第一次被举报时的内容文字（帖子是"标题\n正文"），最多存 2000 字 |
| `status` | `open` / `resolved` / `rejected` |
| `reporter_count` | 举报人数 |
| `created_at` / `updated_at` | 时间 |
| `handled_by` / `handled_at` | 处理人、处理时间 |
| `action` | 处理时做了什么，如 `delete` / `clear` / `rename` / `none` |
| `ban_days` | 封号天数；null 表示不封，0 表示永久 |
| `note` | 协管写的处理说明，必填，1~200 字 |

- 部分唯一索引：`(target_type, target_id) where status = 'open'`，保证同一内容只有一个待处理的案子。
- 索引：`(shard_id, status, updated_at)`。

**`report_entry`**：一个人的一次举报。

| 列 | 说明 |
|---|---|
| `case_id` | 所属案子 |
| `reporter_account_id` / `reporter_rest_id` | 举报人 |
| `reason` | `abuse` / `porn` / `ad` / `politics` / `other` |
| `detail` | 补充说明，0~100 字 |
| `created_at` | 时间 |

- 唯一约束：`(case_id, reporter_account_id)`。

### 3.2 玩家举报

接口：`POST /report`，body 是 `{ targetType, targetId, reason, detail? }`，走 `runOp`，功能开关 `report`（默认开）。

**规则**：
1. 被举报的内容必须存在、没删除、在本区服。店名和公告的 `targetId` 是餐厅 id；公告为空时报 `report_empty`。
2. 不能举报自己的内容：`report_self`。
3. 每账号每天最多举报 `tuning.report.dailyMax` 次（默认 10），超过报 `report_daily`。用的是每日计数。
4. 查找这条内容的待处理案子：
   - 有：加一条举报（同一人第二次报 `report_dup`），`reporter_count + 1`。
   - 没有：先看最近一次已驳回的案子。快照和当前内容相同时，只记数（加一条举报、`reporter_count + 1`），不开新案，玩家看到的结果相同；不同就开新案，快照存当前内容。已处理（resolved）的内容已经被删或改了，正常开新案。
5. 返回 `{ ok: true }`。前端提示"已收到举报，协管会尽快处理"。

**前端入口**：
- 论坛帖子详情、每条回复的菜单里加"举报"。
- 新闻里喇叭那一条旁边加"举报"。
- 好友店铺页（`FriendRestView`）的店名、公告旁边加"举报"。
- 点开是一个小弹窗：选理由，写补充说明，点"提交"。

### 3.3 协管处理

**后台新页"举报"**（`/admin/reports`，协管能进）：
- 筛选：区服、状态（默认待处理）。
- 列表：内容类型、快照（截断显示）、被举报店名和账号、举报人数、最早和最近举报时间。待处理的按人数降序，再按最近举报时间降序。
- 点开详情：
  - 快照和当前内容；当前内容已经没了的写"已删除"或"已改"。
  - 举报人列表：店名、理由、补充说明、时间。
  - 被举报账号已被处理过几次。
  - 两个按钮："处理""驳回"。

**处理**：`POST /admin/reports/:id/resolve`，body 是 `{ note, banDays?, newName? }`，协管能用。
- 按类型执行：

  | 类型 | 操作 |
  |---|---|
  | `post` | 软删除帖子（和管理员删帖同一个函数），撤下对应新闻 |
  | `reply` | 软删除回复 |
  | `broadcast` | 删掉那条新闻 |
  | `notice` | 公告清空 |
  | `rest_name` | 改名：`newName` 不填就用"餐厅{id}"，校验规则和后台改名一样，写个人日志 `admin.rename` |

- 内容已经不在了（作者自己删了、店主改了公告），就不再做内容操作，`action` 记 `none`，但仍可以封号。
- `banDays`：协管只能填 1 或 7；管理员还能填 0（永久）；不填表示不封。不合法报 403 `FORBIDDEN`。
- 案子标为 `resolved`，记录处理人、时间、action、封号天数、说明。
- 在同一个事务里写审计，动作 `report.resolve`。

**驳回**：`POST /admin/reports/:id/reject`，body 是 `{ note }`。案子标为 `rejected`，审计动作 `report.reject`。

**邮件**（`sendMail`，来源 `report`，单店，没有附件）：
- 处理后给每个举报人发：标题"举报结果"，正文"你举报的{类型}已处理，感谢你维护小镇。"
- 驳回后给每个举报人发：标题"举报结果"，正文"你举报的{类型}经核实未违规。"
- 处理后给被处理人发：标题"违规处理通知"，正文写"你的{类型}因违规已被{处理方式}"；封号时写封多久；最后附上协管写的说明。

已经处理或驳回的案子不能再处理，报 `report_closed`。

## 4. 封号期限（6B-1）

**数据**：迁移 0019 给 `account` 加 `banned_until`（可空），null 表示永久。

**封号**：`POST /admin/players/:id/ban`，body 改为 `{ reason, days? }`。
- `days` 取 1、7、0（永久）。不填按永久处理，兼容旧调用；协管不填或填 0 报 403。
- 写 `banned_at`、`ban_reason`、`banned_until`；照旧清掉这个账号的全部会话。

**解封**：`POST /admin/players/:id/unban` 改为只有管理员能用。

**判断是否在封号中**：一个函数 `isBanned(row, now)`，规则是 `banned_at` 不为空，并且 `banned_until` 为空或晚于现在。
- 用在：登录、`requireRole`、后台玩家页显示（"封号至 X 月 X 日"或"永久封号"）。
- 到期后不自动清字段，登录时判断就够了。

**权限矩阵测试**：同步更新——`unban` 改成 admin，新增两个举报接口（mod）。

## 5. 可疑数据页（6B-2）

后台新页"可疑数据"（`/admin/suspicious`，协管能看），按当前选中的区服。四个标签，每行都能点进玩家页：

| 标签 | 数据来源 | 显示 |
|---|---|---|
| 酒吧 | 每日计数 `bar.memory.perfect`、`bar.darts.bull`，最近 7 个游戏日 | 每家店 7 天合计、单日最高；单日超过门槛（`tuning.ops.suspicious.barPerfectDaily` 默认 3，`dartsBullDaily` 默认 20）的标红，按单日最高排序，取前 50 |
| 资源暴涨 | 某个游戏日的流水，按店汇总银币、钻石、经验的净增 | 三项各列前 50，每行附上金额最大的 3 个来源。日期可选，默认昨天 |
| 多号 | 新表 `login_trace` | 同一 IP 或同一设备、最近 30 天内登录过不少于 `tuning.ops.suspicious.sharedAccounts`（默认 3）个账号的，按 IP 或设备分组列出账号和各自在本区服的店 |
| 兑换码被锁 | Redis 键 `redeem:fail:*`，计数不少于 `failLimit` | 账号、次数、剩余锁定时间 |

**`login_trace`（迁移 0020）**：

| 列 | 说明 |
|---|---|
| `account_id` | 账号 |
| `ip` | IP |
| `device_id` | 设备，可为空 |
| `first_seen` / `last_seen` | 首次、最近一次看到的时间 |

- 唯一约束：`(account_id, ip, coalesce(device_id, ''))`。
- 在注册、登录成功时 upsert。
- worker 每天删掉 `last_seen` 超过 30 天的行，任务名 `login-trace-clean`。

**说明**：同一宿舍或网吧的人会共用 IP，页面顶部写明"只作提醒，不能单凭这里处罚"。

## 6. 区服数值说明（问题记录 126，6B-2）

**说明文件** `packages/config/data/game/setting_docs.json`：

```json
{
  "features": { "mail": "邮箱：……", "...": "..." },
  "groups": { "tuning.settlement": "结算：……", "restaurant": "开店默认值：……" },
  "fields": { "tuning.settlement.expMultiplier": "结算经验倍率（倍数，1 = 原版）", "...": "..." }
}
```

- 要覆盖所有功能开关（`IMPLEMENTED_FEATURES`）、所有分组（`tuning.xxx` 和 `restaurant`）、所有叶子路径。
- 叶子路径的规则：对象逐层展开；数组算一个叶子，比如 `restaurant.giftFoods`。
- 写说明的原则：一句话说清楚管什么，带单位（秒、分钟、游戏日、倍数、0~1 的概率、百分比、银币等），有特殊值的写出来（比如"0 表示不限"）。

**构建**：
- 说明文件进配置包，构建时交叉检查：
  - 漏写的报错 `setting_docs missing tuning.xxx.yyy`；
  - 写了已不存在的路径报错 `setting_docs unknown tuning.xxx`。
- 说明随 `ShardSettingsDto` 下发（新增字段 `docs`）。

**后台区服数值页**：
- 每项字段名下面显示说明（小字灰色）；每组标题旁显示组说明；功能开关的复选框悬停显示说明，下面也用小字写出。
- 顶部加搜索框，按字段名或说明过滤：匹配的项所在分组自动展开，不匹配的隐藏。

## 7. 上线检查（6B-2）

**检查项**：代码里一张表 `LAUNCH_CHECKS`，每条写明路径、上线时应为什么值、为什么。

| 路径 | 上线值 | 为什么 |
|---|---|---|
| `tuning.hiphop.requireVerifiedEmail` | true | 防止小号刷嘻哈奖励 |
| `tuning.town.shake.limitIp` | true | 摇钱树按 IP 限次，防多号 |
| `tuning.town.shake.limitDevice` | true | 摇钱树按设备限次，防多号 |
| `tuning.friend.requireVerifiedEmail` | true | 好友互动要求验证邮箱（现在已经是 true，一起盯着防止被改回去） |

**接口**：
- `GET /admin/launch-check`（协管能看）：每个开着的区服，每项给出当前生效值、是否通过。
- `POST /admin/launch-check/fix`（管理员）：body 是 `{ shardId }`，把这个区服没通过的项写进区服覆盖。
  - 走现有的区服数值保存函数，修改说明写"上线检查"，所以修改历史、审计、设置缓存刷新都照旧。
  - 带上当前版本号，防止并发冲突。

**后台概览页**：加一块"上线检查"。全部通过显示绿色"可以上线"；否则逐个区服列出没通过的项和原因，每个区服一个"改成上线值"按钮（只有管理员看得到），点之前要确认。

**默认值不动**：开发环境和 e2e 不受影响。

## 9. 错误原因（`INVALID_STATE` 的 reason，前端补中文）

| reason | 中文 |
|---|---|
| `report_self` | 不能举报自己 |
| `report_dup` | 你已经举报过这条内容了 |
| `report_daily` | 今天的举报次数用完了 |
| `report_empty` | 这家店没有公告 |
| `report_closed` | 这条举报已经处理过了 |

## 10. 测试要点

**举报**：
- 五种内容都能举报；
- 自己的内容不能举报；
- 每日上限；
- 同一人重复举报；
- 多人挂到同一个案子；
- 驳回后同样内容只记数不开新案，内容改了开新案；
- 并发：两个人同时举报同一内容，只开一个案子（靠部分唯一索引）。

**处理**：
- 每种类型的操作都执行到；
- 内容已经不在时 action 记 `none`；
- 协管不能永封，管理员能；
- 邮件发给举报人和被处理人；
- 审计；
- 已结案的不能再处理。

**封号期限**：
- 1 天的封号，到期后能登录；
- 永久封号一直不能登录；
- 协管不能解封。

**可疑数据**：四个标签各一个查询测试；`login_trace` 的 upsert 和清理。

**数值说明**：
- 漏写、多写都报构建错误；
- 后台搜索过滤。

**上线检查**：
- 未通过的项列出来；
- 一键修复后全部通过；
- 修改历史有一条"上线检查"；
- 协管不能修复。

**164~170**：各一个前端测试。

**e2e**：
- 6B-1：玩家 A 举报玩家 B 的公告，管理员在后台处理，B 的公告被清空，A 收到结果邮件。
- 6B-2：管理员在概览页一键修复上线检查。注意不要改开发库的区服数值——e2e 新建一个自己的区服来测。
