# 限时活动 148-3：全服合力 设计

日期：2026-10-02
状态：待用户审阅

## 1. 范围

问题记录 148 的最后一个子项目（顺序 1 → 4 → 2 → 3）。一个 PR，分支 `feat/activity-coop`。

在 148-1 的活动框架里加第六种类型 **全服合力**（`coop`）：

- 玩家照常玩，行为按分计入个人贡献；
- 本区服所有店的贡献加起来就是全服总分；
- 全服总分到达里程碑后，个人贡献达到门槛（至少 1 分）的店可以领里程碑礼包；
- 活动结束后，按个人贡献排名，给各名次段发奖励。

## 2. 用户已确认的裁定

1. 里程碑礼包发给**个人贡献 ≥ 门槛**的店。门槛按里程碑在后台填，可以填 0。
2. 贡献点只来自**行为计分**：和战令一样，每条规则是"行为、每次几分、每天上限"。不做捐献。
3. 全服活动（不限区服）时，**每个区服各自一个池**：总分、里程碑、贡献榜都按区服分开。
4. 贡献榜**按名次段发奖**：活动结束后结算，发邮件，并发一条新闻。
5. 全服总分**在读取时求和**：个人贡献存在各自的计数行里，读取时求和，不另设一行累加，避免同一区服所有玩家争抢同一行。

## 3. 活动定义

shared 的 `ACTIVITY_KINDS` 加 `'coop'`，`ActivitySpec` 加 `{ kind: 'coop'; def: CoopDef }`。迁移 0024 放开 `activity.kind` 的检查约束（约束名 `activity_kind_check`）。

```ts
CoopDef = {
  rules: { key: ActionKey; points: int 1..1000; dailyCap: int 1..100000 }[1..20],  // 同战令，行为不重复
  milestones: {
    target: int 1..1_000_000_000,     // 全服目标分，逐个严格递增
    minContribution: int 0..100_000_000, // 个人最低贡献，0 = 有贡献（至少 1 分）就行（终审 I1）
    award: rewardItems,
  }[1..10],
  ranks: {
    from: int 1..100,                 // 第几名起
    to: int 1..100,                   // 到第几名（含），from ≤ to
    award: rewardItems,
  }[0..10],                           // 按 from 升序，前后不重叠；可以不连续
}
```

校验错误带字段路径（错误码）：
- 规则行为重复（`duplicate_key`）；
- 里程碑目标分不递增（`not_increasing`，挂在后一个里程碑的 `target` 上）；
- 名次段 `from > to`（`bad_range`）、和上一段重叠或没按升序（`overlap`，挂在这一段的 `from` 上）。

开始后定义不能改（148-1 规则），所以里程碑和名次段的下标是稳定的。

## 4. 计数

和战令走同一段代码（`modules/activity/handler.ts` 的 `count`）：

- 找到 `key` 等于本次行为的规则；
- `add = min(points × n, dailyCap − 今天已加)`；
- 今天已加的分记在 `daily_counter`，键 `act<活动id>:<行为键>`（沿用 `passDailyKey`）；
- 个人贡献加在 `activity_counter (活动, 店, 'points')`。

活动窗口、区服、等级门槛、功能开关的判断都沿用原来的。

## 5. 全服总分和贡献榜

### 5.1 求和

```sql
select coalesce(sum(c.count), 0)
from activity_counter c join restaurant r on r.id = c.rest_id
where c.activity_id = $1 and c.key = 'points' and r.shard_id = $2
```

- 新函数 `poolOf(db, activityId, shardId): Promise<number>`。
- 新函数 `topOf(db, activityId, shardId, limit)`：同一个连接条件，按积分从高到低、店 id 从小到大排序。返回名次、店 id、店名、积分。

### 5.2 名次

纯函数 `rankRows(rows: { restId; points }[]): { restId; points; rank }[]`：

- 积分为 0 的不上榜；
- 按积分从高到低排；
- 同分同名次，下一个名次跳过并列的人数（例如 1、1、3）。

店 id 只用来让顺序稳定，不影响名次。

### 5.3 缓存

玩家列表里的总分、前 10 名、我的名次，按"活动 + 区服"在本进程缓存 30 秒（`Map`，过期时间戳）。

- 我的名次 = 积分比我高的店数 + 1。我的积分为 0 时没有名次。这个数单独查，不走缓存，因为我刚加的分要立刻看得到。
- 领取、补发不走缓存，都在事务里重新求和。

## 6. 达成和领取

- `rewardsOf(spec, counters, premium, ctx?: { pool?: number })` 多一个可选参数，其他类型忽略它。
- 合力类型返回每个里程碑一份奖励，键 `s<下标>`：
  - `reached = pool ≥ target && 个人贡献 ≥ max(1, minContribution)`（终审 I1：门槛为 0 也要有贡献）；
  - 个人贡献就是 `counters.points`，没有则为 0。
- 名次段奖励**不**放进 `rewardsOf`：它们只在结算时发，不在页面领取（§7）。
- 领取沿用现有的 `claim` / `claimAll`。合力活动在锁店事务里先 `poolOf(o.tx, …)`，再用它算 `rewardsOf`。
- 玩家 DTO 的 `rewards`、`claimable` 也用 §5.3 的缓存总分算。缓存最多晚 30 秒，所以页面显示的"可领"可能比实际晚一点。领取时以事务里的实时总分为准：页面先显示可领而实时未达成的情况不会出现，因为总分只会增加。

## 7. 结束结算

沿用补发任务 `activity-settle`：每分钟按区服跑，结束 2 分钟后开始。合力活动在这个区服的处理顺序：

1. **里程碑补发**：先算一次本区服的 `pool`，然后像其他类型一样逐店补发达成但没领的里程碑，`rewardsOf` 传入这个 `pool`。
2. **贡献榜**：用 §5.2 算本区服的完整名次。对每个名次段，名次在 `[from, to]` 内的店都发奖。段边界上并列的全部发奖，所以实际人数可能比段宽多。
   - 每家店一个锁店事务，先写领奖记录（`reward_key = 'r<段下标>'`，`via = 'mail'`，冲突就跳过），写成功了才发邮件，所以重跑不会重复发。
   - 邮件标题"《活动名》贡献榜第 N 名奖励"，正文"感谢你为全服合力做出的贡献，这是你的名次奖励。"，来源 `activity`。
3. **新闻**：本区服有人上榜时，发一条新闻 `activity.coopRank`，参数：活动名，以及前 3 名的店名、积分、名次。
   - 只在第 1、2 步所有店都成功时才进行；有店失败时，这一轮不写 `activity_settle`、不发新闻，下一分钟重试。
   - 新闻和"写结算完成"在同一个事务里：先插 `activity_settle`（冲突就跳过），确实插入了新行才用 `postNews` 发新闻。所以重跑不会重复发新闻。

前端新闻文案："《国庆合力》贡献榜：第 1 名 甲餐厅（1,234 分）、第 2 名 乙餐厅（1,100 分）、第 3 名 丙餐厅（990 分）"。

## 8. 玩家 DTO 和前端

### 8.1 DTO

`ActivityDto` 加：

```ts
coop: {
  pool: number;
  top: Array<{ rank: number; restId: number; name: string; points: number; mine: boolean }>; // 前 10 名；mine = 是不是我的店（前端没有店 id，加粗自己用）
  myRank: number | null;
} | null;  // 其他类型为 null
```

### 8.2 玩家卡片 `ActivityCoop.vue`

- 第一行："全服 12,345 分 · 我的贡献 230 分 · 第 5 名"（没名次时不写名次）。
- 进度条：从上一个里程碑到下一个里程碑的进度。全部达成时显示满格和"全部里程碑已达成"。
- "今天："各规则的已得分/上限，和战令一样。
- 里程碑列表：目标分、个人门槛（0 时不写）、奖励，用现有的领奖按钮。
  - 全服已达成、个人贡献不够时，显示"个人贡献还差 N 分"。
  - 全服未达成时，显示"全服还差 N 分"。
- 贡献榜：
  - 名次段奖励列表（"第 1 名：…""第 2~3 名：…"）；
  - 前 10 名表格（名次、店名、积分），自己的店加粗；
  - 活动结束后在上方显示"贡献榜已结算，奖励已发邮件"（`state === 'ended'`），结算中时显示"贡献榜结算中"。
- `ActivitiesView.vue` 用显式的 `v-else-if="a.kind === 'coop'"` 分支。

### 8.3 后台编辑器 `CoopEditor.vue`

- 类型下拉加"全服合力"。
- 计分规则表：把 `PassEditor.vue` 里的规则行抽成共用组件 `RuleRows.vue`，战令和合力都用它。
- 里程碑表：目标分、个人门槛、奖励编辑器（`RewardItemsEditor`，可以选帽子），可增删，最多 10 行，行用 `rowKeys`。
- 名次段表：从、到、奖励编辑器，可增删，最多 10 行，行用 `rowKeys`。
- 字段错误显示在对应行，测试 id 用 `err-<路径>`。
- `activityForm.ts`：`defaultDef('coop')` 给一条签到规则、一个里程碑（目标 1000、门槛 0）、一个名次段（第 1~1 名）；`TEXT` 加 `bad_range: '起始名次不能大于结束名次'`、`overlap: '名次段不能重叠，要按名次从小到大排'`。

### 8.4 其他

- 首页横幅"进行中的活动 N 个"照常计入合力活动。
- 后台列表的"参与店数"照常（有计数行的店）。

## 9. 测试

- 定义校验：§3 每种错误都带路径；`ranks` 可以为空。
- 纯函数：
  - `rankRows`：同分同名次（1、1、3）；积分 0 不上榜；
  - `rewardsOf`（合力）：总分够、个人不够时不达成；都够时达成；不传 pool 时按 0 算。
- 集成：
  - 计数：和战令一样有每天上限；
  - 两个区服的总分互不影响；全服活动（`shard_id` 为空）在两个区服各自求和、各自结算；
  - 领取：总分不够时报 `requirement('activity')`；够了能领，领过再领报已领；
  - 补发任务：
    - 里程碑补发和名次段奖励都发出邮件；
    - 段边界并列的两家店都发；
    - 积分 0 的店不发；
    - 重跑不重复发邮件、不重复发新闻；
    - 每个区服一条新闻；
  - 列表 DTO 的 `coop`：总分、前 10 名、我的名次，非合力类型为 null。
- 前端：
  - 卡片：总分、名次、进度条、两种"还差 N 分"、前 10 名、自己加粗、结束提示；
  - 后台：三张表的增删、提交内容、行内错误；
  - 战令编辑器改用共用的规则行后原有测试仍然通过；
  - 新闻文案。

## 10. 不做的事

- 捐献换贡献点。
- 跨区服合并的总池。
- 贡献榜实时推送、名次变化提醒。
- 名次并列时按先到达排序（需要记录加分时间）。
