# 自由交易市场 156-3：系统做市 设计

日期：2026-10-02
状态：用户已审阅

## 1. 范围

问题记录 156 的最后一个子项目（顺序 1 → 2 → 3）。一个 PR，分支 `feat/exchange-maker`。

给交易所加一个**系统做市商**：

- 玩家想卖时，总有人以低于参考价的价格接盘；
- 系统收进来的货，玩家想买时能以高于参考价的价格买到；
- 买卖之间的差价就是银币回收。

## 2. 用户已确认的裁定

1. **系统库存做市**：系统只卖自己从玩家手里收进来的食材，不凭空造食材。
2. **价格**：
   - 收购价 = 参考价 × 0.7，并封顶到"菜场里能买到这种食材的最低价 × 0.9"，防止玩家在菜场低价买进、再卖给系统套利；
   - 卖出价 = 参考价 × 1.3。
3. **上限**：区服和个人都限。
   - 每个区服每种食材：每天最多收 100 个，库存最多 500 个；
   - 每个玩家每天卖给系统最多 20 个（所有食材合计）。
4. **参考价不受影响**：和系统的成交**不算**进每日参考价，避免系统报价和参考价互相拉动。
5. **实现方式**：撮合时临时算出系统报价，当作盘口里的一档参与成交，不存成挂单。

## 3. 区服数值

`tuning.exchange.maker`（`tuning.json`、zod、`setting_docs.json` 都要加）：

```jsonc
{
  "enabled": true,
  "bidRate": 0.7,        // 收购价 = 参考价 × bidRate（向下取整）
  "askRate": 1.3,        // 卖出价 = 参考价 × askRate（向上取整）
  "marketCapRate": 0.9,  // 收购价不超过 菜场最低价 × marketCapRate
  "dailyBuy": 100,       // 每个区服每种食材每天最多收多少
  "stockMax": 500,       // 每个区服每种食材库存上限
  "playerDaily": 20      // 每个玩家每天卖给系统的总数上限
}
```

## 4. 报价

### 4.1 菜场最低价

`marketFloor(food, config, marketTuning, priceFactor)`：这种食材在菜场里可能的最低单价；菜场不卖的返回 `null`。

- 这种食材可能出现在哪些货架，按菜场进货用的食材池判断（`config.foodPools`）：
  - 日常货架：等级在 `dailyLevelWeights` 里、并且在该等级的池子里，单价是系统定价。手动进货也上日常货架，按同样规则。
  - 特价货架：等级在 `specialLevelWeights` 里、并且在池子里，或者在热门稀缺食材池（`config.hotFoodPool`）里，单价是 `specialPrice`。
  - 高级货架：等级等于 `premiumLevel`、并且在池子里，单价是系统定价 × `premiumPriceFactor`。
- 取上面能出现的货架里最便宜的单价，再乘：
  - 最便宜天气的系数 `1 + min(marketCoin)`（现在的数据里是 1 − 0.3 = 0.7）；
  - 当前区服数值里的 `market.priceFactor`。全服加成给菜场打折时它小于 1，所以封顶也跟着降。

### 4.2 系统的买价和卖价

参考价 `ref` 是当天参考价（156-1 §5），允许范围 `[min, max]`（156-1 §5）。

- **买价**：`floor(ref × bidRate)`。菜场最低价不为空时，再取 `min(买价, floor(菜场最低价 × marketCapRate))`。高于 `max` 取 `max`；**低于 `min` 就没有买这一档**（不往上抬，否则封顶失效）。
  - 现有数据下 3~5 级食材会上特价货架，封顶约 1,889，低于它们的挂单下限（参考价最低 3,800 × 0.5），所以系统不收 3~5 级（用户已确认：严格封顶）。系统做市实际只覆盖 1、2、6、7、9 级。
- **卖价**：`ceil(ref × askRate)`，夹到 `[min, max]` 里。
- **能收的数量**：`min(dailyBuy − 今天已收, stockMax − 库存, playerDaily − 这个玩家今天已卖给系统)`。小于等于 0 就没有买这一档。
- **能卖的数量**：库存。为 0 就没有卖这一档。
- `enabled = false` 或区服关了交易所时，没有系统报价。

### 4.3 撮合

在 156-1 的撮合循环里，系统报价是盘口里的一档：

- **价格优先**：
  - 玩家卖单吃买单时，系统买价比当前玩家买单高，就先和系统成交；
  - 玩家买单吃卖单时，系统卖价比当前玩家卖单低，就先和系统成交。
- **同价时玩家的单先成交**，系统排最后。
- **新单是卖单**，在价格允许范围内，系统买价 ≥ 卖价时可以卖给系统，数量按 §4.2 的"能收的数量"。
- **新单是买单**，系统卖价 ≤ 买价时可以从系统买，数量按库存。
- **一次下单里的数量**：和系统成交的数量计入当次的"今天已收""库存""这个玩家今天已卖"，所以同一次下单里不会超过上限。

和系统的一笔成交：

- **卖给系统**：
  - 玩家得 `价格 × 数量 − 手续费`，手续费照常是 5%；
  - 系统库存加上这些食材，今天已收、玩家今天已卖都相应增加。
- **从系统买**：
  - 玩家得到食材，冻结的银币里多出的差价照常退回；
  - 系统库存扣掉这些食材。
- **成交记录**：`exchange_trade` 写一行，`system = true`。
  - 系统那一方的店和账号为空；
  - 没有可疑标记，也不进冷静期；关联账号判定只针对玩家挂单方，不涉及系统。
- **不计入**：
  - 参考价的加权均价（单个算和批量算两处都要排除）；
  - "反复对倒"的计数（系统那一方没有账号，本来就对不上）。
- **被冻结的店**：照样不能下单（156-2）。

### 4.4 并发

系统库存和每日收购计数在盘口锁里读写（同一区服同一种食材是同一个盘口），所以不会超卖或超收。

玩家每天卖给系统的数量用现有的 `daily_counter`，键为 `exchange.toSystem`。它在玩家自己的锁店事务里更新，所以玩家并发下单时也不会超限。

## 6. 盘口和查询

- `GET /exchange/book/:foodsId`：系统那一档合并进 `bids` / `asks`。每档加 `system: boolean`；系统和玩家同价时分成两档，系统排在后面。
- **最新成交价**（列表的 `last`、`changePct`，盘口的 `last`）只看玩家之间的成交；**今日成交量**（盘口的 `volume`）包括和系统的成交。
- `GET /exchange/me` 的成交记录：和系统的成交照常显示，加 `system: true`，前端写"（系统）"。
- **前端盘口**：系统那一档写"系统"，用不同的颜色。

## 7. 后台

在"可疑数据 → 交易所"标签下面加一节"系统做市"，只读，`mod` 可看，按区服：

- `GET /admin/exchange/maker?shardId`：
  - 每种有库存或今天有收购的食材：库存、今天已收、当前的系统买价和卖价；
  - 今天系统收购花了多少银币、卖出收回多少（卖出所得按成交额算）、净回收多少（收回减去花出，加上卖给系统那一侧的手续费）。

后台权限矩阵测试要加上这条路由。

## 8. 测试

- **纯函数**：
  - 菜场最低价：日常、特价、高级三种货架；最便宜的天气；`priceFactor` 打折；菜场不卖的返回 null。
  - 系统买价：按参考价 × 0.7；被菜场价封顶；夹在允许范围内。
  - 系统卖价：参考价 × 1.3，夹在允许范围内。
- **撮合**：
  - 卖给系统：扣手续费；库存、今天已收、玩家今天已卖各自增加；
  - 从系统买：只卖库存，卖完就没有这一档；
  - 同价时玩家的单先成交；价格更好时系统先成交；
  - 三个上限各自生效，同一次下单里也累计；
  - 系统成交不进参考价、不算反复对倒、不冻结；
  - `enabled = false` 时没有系统报价；
  - 并发：两个玩家同时卖给系统，合计不超过今天的收购上限。
- **守恒**：玩家食材 + 系统库存的总数不变；所有玩家的银币变化合计 = −（系统净收支）− 手续费。
- **查询**：盘口的系统档；后台汇总；权限矩阵。
- **前端**：盘口的"系统"档和颜色、成交记录里的"（系统）"、后台"系统做市"一节。

## 9. 不做的事

- 系统主动按市场情况调整价差、库存过期销毁。
- 系统给道具做市。
- 系统库存的后台手动调整。
