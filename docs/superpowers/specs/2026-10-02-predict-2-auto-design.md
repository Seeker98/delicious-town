# 事件合约 238-2：系统自动出题 设计

日期：2026-10-02
状态：待用户审阅

## 1. 范围

问题记录 238 的第二部分。合约引擎、管理员出题、结算、页面已在 238-1（PR #59、#60）完成。本 PR 只加**系统自动出题和自动判定**。分支 `feat/predict-auto`，依赖 PR #61（随机种子混入 `RNG_SECRET`，否则纯随机类题目能按公开源码算出结果）。

## 2. 用户已确认的裁定

1. **题型**：蟹老板、嘻哈男孩、菜场货架、天气、全服数据都做；全服合力"能否到下一档"以后再加。
2. **节奏**：每个区服每天每类 1 题，共 4 题；蟹老板和嘻哈男孩隔天轮换。
3. **天气**：以整点自动轮换的天气为准，之后用雷神锤改的不算；判定时写清"判定依据"，让玩家明白结果为什么和眼前天气不一样。
4. **数据、任务、页面**：按 §5~§7。自动判定不需要管理员确认；管理员仍可手动判定或作废，覆盖自动判定。

## 3. 区服数值

`tuning.predict.auto`（`tuning.json`、zod、`setting_docs.json` 都要加）：

```jsonc
{
  "krab": true,          // 蟹老板 / 嘻哈男孩题（隔天轮换）
  "market": true,        // 菜场货架题
  "weather": true,       // 天气题
  "stats": true,         // 全服数据题
  "b": 100,              // 自动题的流动性
  "marketCloseMin": 5,   // 菜场题在开货前几分钟截止
  "statsCloseHour": 18   // 全服数据题当天几点截止
}
```

## 4. 四类题目

出题时间是每天 0 点后第一次跑任务时（游戏时间，下同），记当天为 D。出题用的随机（选街段、地点、时段等）用服务器随机源 `d.rng()`，不用确定性种子。

### 4.1 蟹老板（D 为单数日，按游戏日期的日子奇偶）

- **标题**："明天蟹老板会在 a~(a+5) 号街出现吗"。a 在 `[krabStreetMin, krabStreetMax − 5]` 里随机。
- **说明**："以明天 9 点（krabHour）系统刷新的位置为准，之后被驱赶改变的不算。"
- **初始概率**：`6 / (krabStreetMax − krabStreetMin + 1)`，现在是 6/13。
- **截止**：D 当天 23:50。
- **判定时间**：D+1 的 krabHour 之后。
- **判定**：按 `rollKrabStreet(tuning.world, seededRng(gameSeed(shardId, 'krab', slotKey(D+1, krabHour))))` 重算那一刻刷新出的街，和世界服务的刷新完全一致。
- **判定依据**：例如"明天 9 点蟹老板刷新在 7 号街"。

### 4.2 嘻哈男孩（D 为双数日）

- **标题**："明天嘻哈男孩会出现在 X 吗"。X 按 `hiphop.placeWeights` 的权重抽一个地点，地点名用 `HIPHOP_PLACE_NAMES`。
- **初始概率**：X 的权重 ÷ 总权重。抽到"某家餐厅"那一项时，题目写"会去某家玩家餐厅吗"。
- **截止**：D 当天 23:50。
- **判定时间**：D+1 的 `hiphop.hour` 之后。
- **判定**：读 `hiphop_day`（D+1）的地点。记录还没生成就等下一分钟；仍判不出来按 §5.3 处理。
- **判定依据**：例如"明天嘻哈男孩出现在广场"。

### 4.3 菜场货架

- **时段 H**：从 `market.dailyHours` 里随机选一个，要满足 `H 点 − marketCloseMin` 晚于出题时间至少 1 小时。
- **等级 L**：1 或 2。用 `rollShelf(0, H, …)` 配随机种子模拟 2,000 次，估算"至少一种 L 级稀有食材（odds < 100）上架"的概率，取 1、2 级里离 50% 更近的那个。概率夹在 5%~95%。
- **标题**："今天 H 点的日常货架会出现 L 级稀有食材吗"。
- **截止**：H 点前 `marketCloseMin` 分钟。
- **判定时间**：H 点之后。
- **判定**：读 `market_item`：本区服、日常货架、`period = slotKey(D, H)`，看有没有 L 级、odds < 100 的食材。货架还没生成就等下一分钟。
- **判定依据**：列出这一轮上架的稀有食材，例如"12 点日常货架上了 2 级稀有：松茸、藏红花"；没有就写"没有 L 级稀有"。

### 4.4 天气

- **时段 H**：从 `world.weatherHours` 里随机选一个，要满足 H 点比出题时间晚至少 3 小时。
- **天气类型 X**：从 晴类（type 1）、雨类（2）、雪类（3）、风沙雾霾类（4）里随机选一个，要满足它在 H 点天气池（`weatherPool(config, isNight(H), world)`）里的权重占比在 15%~85% 之间；都不满足就选占比最接近 50% 的。初始概率就是这个占比。
- **标题**："今天 H 点自动轮换的天气是X类吗"。
- **说明**："以 H 点系统自动轮换出的天气为准，之后有人用雷神锤改的不算。"
- **截止**：上一个天气时段结束前 5 分钟，也就是 H 点前 5 分钟。
- **判定时间**：H 点所在时段结束后（H + 2 小时），这样判定依据能写全这段时间里的雷神锤改动。
- **判定**：按 `rollWeather(config, H, tuning.world, seededRng(gameSeed(shardId, 'weather', slotKey(D, H))))` 重算自动轮换的天气，看它的 type 是不是 X。
- **判定依据**："H 点自动轮换的天气是小雨（雨类）"。如果这个时段里有人用雷神锤改过（`news` 里 `type = 'weather.change'` 且带 `by` 的记录），再加一句"之后有人用雷神锤改成了晴，按题目规则不算"。改过多次就写最后一次。

### 4.5 全服数据（营业银币、活跃店数隔天轮换）

- **标题**：
  - "今天全服营业银币会超过昨天吗"：用 `aggregateDay` 里的 `coin / settlement`；
  - "今天全服活跃店数会超过昨天吗"：用 `active / rest`。
- **初始概率**：50%。
- **截止**：D 当天 `statsCloseHour` 点。
- **判定时间**：D+1 的 00:10 之后。
- **判定**：用 `aggregateDay(db, shardId, D)` 和 `aggregateDay(db, shardId, D−1)` 比较，严格大于才算"是"。
- **判定依据**：例如"今天 12,345,678，昨天 11,000,000"。

## 5. 任务和数据

### 5.1 迁移 0031

```
predict_event
  auto_key     text            -- 例如 'krab:2026-10-03'、'weather:2026-10-03'；手动题为空
  result_note  text            -- 判定依据；手动判定为空
  resolve_at   timestamptz     -- 自动题最早什么时候判定；手动题为空
unique index (shard_id, auto_key) where auto_key is not null
```

自动题的 `kind` 写题目类型（`krab`、`hiphop`、`market`、`weather`、`stats`），出题人 `created_by` 为空，判定参数存在 `params` 里，例如 `{ "from": 1, "to": 6 }`、`{ "hour": 12, "level": 2 }`。

### 5.2 出题任务 `predict-auto-create`

- **触发**：每天一次，周期键为游戏日 D；挂在 `predict` 功能上，区服关掉事件合约就不出题。
- **出题**：每类题目开关打开时出一题，蟹老板 / 嘻哈男孩按日期奇偶二选一，写 `auto_key = '<类型>:<D>'`。
  - 插入时遇到唯一冲突就跳过，所以任务重跑不会重复出题。
  - 出题时 `unit` 照常从区服数值复制，b 用 `auto.b`。
- **出不了题**（比如没有满足条件的时段）就跳过这一类，记一条日志。
- **依赖的功能被关掉时不出这一类**：菜场题看 `market`，嘻哈男孩题看 `hiphop`（这天改出蟹老板题），天气题和蟹老板题看 `world`。

### 5.3 判定任务 `predict-auto-resolve`

- **触发**：每分钟一次，挂在 `restaurant` 功能上，区服关掉事件合约时已出的题照常判定。
- **处理范围**：`auto_key` 不为空、状态是 open 或 closed、`resolve_at ≤ now` 的事件。
  - 调这一类的判定函数，返回 `{ outcome, note }` 或"还判不了"。
  - 判出来了：锁事件行，状态仍是 open 或 closed 时改成 resolved，写 `outcome`、`result_note`、`resolved_at`。管理员已经手动判定或作废的不动。结算照常由 `predict-settle` 做。
  - `resolve_at` 过了 24 小时还判不了：作废（和管理员作废一样，按比例退款），`result_note` 写"数据缺失，自动作废"。
- **审计**：自动判定不写审计日志（审计只记人工操作），判定依据存在事件里。

### 5.4 结构

`apps/server/src/modules/predict/auto/`：

- **每类一个文件**（`krab.ts`、`hiphop.ts`、`market.ts`、`weather.ts`、`stats.ts`），各自导出一个对象：
  - `kind`；
  - `create(ctx)` 返回 `{ title, description, p0, closeAt, resolveAt, params } | null`；
  - `resolve(ctx, event)` 返回 `{ outcome: boolean; note: string } | null`。
- **`index.ts`**：题目列表、出题任务、判定任务。
- **纯函数单独测试**：菜场概率估算、天气类型选择和占比。

## 6. 页面

- **玩家预测页**：
  - 详情和已结束列表显示"判定依据"（`result_note`）；
  - 自动题在标题旁标"系统出题"；
  - DTO 加 `auto: boolean`、`resultNote: string | null`。
- **后台预测页**：
  - 出题人显示"系统"，判定依据显示在状态下面；
  - 管理员手动判定或作废照常可用。

## 7. 测试

- **各类出题**：
  - 标题、初始概率、截止和判定时间符合 §4；
  - 菜场的时段在出题后至少 1 小时；天气的时段在出题后至少 3 小时。
- **各类判定**：
  - 蟹老板按种子重算（配置 `RNG_SECRET` 时也一致）；
  - 嘻哈男孩读地点；
  - 菜场读货架（货架没生成时返回"还判不了"）；
  - 天气按种子重算，雷神锤改过时判定依据里写明；
  - 全服数据严格大于才算"是"。
- **任务**：
  - 出题重跑不重复；
  - 开关关掉不出这一类，区服关掉事件合约不出题；
  - 判定写结果和判定依据；
  - 管理员已手动判定的不覆盖；
  - 24 小时判不了就自动作废。
- **纯函数**：菜场概率估算和直接模拟的结果相差在 3% 以内；天气类型占比和天气池一致。
- **前端**：判定依据、"系统出题"标记、后台显示"系统"。

## 8. 不做的事

- 全服合力题；
- 多选项事件；
- 玩家自己出题；
- 根据成交情况自动调整 b。
