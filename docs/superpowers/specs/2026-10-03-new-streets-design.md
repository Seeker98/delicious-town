# 新街道接入游戏（问题记录 284，路线图第 12 项）

## 1. 目标

把另一个 agent 在 `data/` 下做好的数据接进游戏：

- **老街道修订**（`data/老数据修订/`，方案见 `data/老街道重合调整方案.md`）：
  - 已有菜谱删 32 道、移街 8 道（id 不变），2363 → 2331 道。
- **新街道**（`data/新街道菜谱/`）：
  - 16 条异国街（id 14~29）；
  - 1479 道新菜谱（id 18747~20225）；
  - 23 种新食材（id 584~606，13 种基础 + 10 种高级版）；
  - 16 枚街道勋章（数据里是 goods id 628~643，但这段 id 已被装备设定新增的厨具占用，导入时改成 92000 + 街道 id，即 92014~92029）。
- **菜名译名**（`data/i18n/`）：共 3810 道，英、法、西三种语言。

接入后共 30 条街、3810 道菜谱。

## 2. 用户确认的裁定

1. **新菜谱缺 8~10 品级**：由我按老数据的规律生成（见 §5.3）。生成脚本放进仓库，结果作为静态数据提交。
2. **"全部食谱"门槛跟随实际总数**：
   - 主线任务"把全部食谱升到珍品"，和泛紫 5 星（要求天馔食谱数）现在都写死 2363。
   - 改成构建时取菜谱总数。
3. **开发库的玩家数据加迁移修正**：
   - 清掉被删菜谱的已学记录，重算已学统计；
   - 删掉点了被删菜谱、还能接的外卖单。
4. **蟹老板街道**放开到 1~29。
5. **繁中继续用 OpenCC 自动转换**：不用 `data/i18n/zh-TW` 里带台湾用语的菜名。否则菜名会改成"馬鈴薯"，而食材名还是"土豆"，两边对不上。
6. **不改**：
   - 新食材按等级进入随机掉落池，同等级老食材的份额会略降，接受；
   - 新街勋章的数值按数据上线，以后再调（先出能玩的版本）。
7. **分两个 PR**：先合老街道修订，再接新街道。

## 3. 现状和发现的问题

数据已核对：
- 修订后的老数据和仓库当前版本只差上面 32 删 8 移；
- 新数据引用的食材都存在，菜名不重复，id 与现有数据不冲突；
- 新勋章用到的 17 个加成键在服务端都有读取。

接入会碰到的问题：

| 问题 | 后果 | 处理 |
|---|---|---|
| 街道勋章靠 `type=9 且 devicetype<=13` 识别；雕像勋章的 devicetype 是 20，和印度街 id 撞了 | 数据方案说放宽到 29，那样雕像会被认成印度街勋章 | 显式对应表（§5.4） |
| 探险的神秘食材概率只读灯、针、保安证三样道具 | 摩洛哥街"探险时获得神秘食材概率+2%"不生效 | 探险加上本街勋章的 `mysteriousRate`（§5.5） |
| 已学食谱是按"最大菜谱 id + 1"长度存的字节串；老店的长度是 18747 | 学 id 更大的新菜谱时，写入类型化数组越界会被静默丢掉，学了等于没学 | 读出时补齐到当前长度（§5.5） |
| 删菜、移街后，`restaurants.cookbook_counts`（已学数、各品级数、各街已学数）不再准确 | 星级、任务、菜谱页的"本街已学"出错 | 迁移重算（§4.3） |
| 外卖单、配送记录、外卖页用 `requireCookbook` 取菜谱 | 被删菜谱的单会让外卖页报错 | 迁移删可接单；外卖页容错（§4.3） |
| 新菜谱只有 1~7 品级，构建要求 10 个品级 | 构建失败 | 生成 8~10 品级（§5.3） |
| 任务和星级里写死 2363 | 修订后"全部"不再是全部 | `"all"`（§4.2） |
| 蟹老板街道 `krabStreetMin/Max` 是 1~13 | 新街永远轮不到 | 改成 1~29 |
| 模拟器 `sim/bench.ts`、`sim/bot.ts` 写死 13 条街 | 模拟不到新街 | 改为读配置 |
| 搬家页下拉框只有街名 | 30 条街不好选 | 显示所选街道的加成 |

字符集：
- 越南文、土耳其文这类带附加符号的拉丁字母，界面用的是系统字体，可以正常显示；
- 菜名只存在配置里，数据库里只存 id，所以不需要改字符集。

## 5. PR 2：新街道接入

### 5.1 数据文件

新内容单独放文件，构建时合并。原游戏抓来的 `dataset/` 不再追加内容。

| 文件 | 内容 | 来源 |
|---|---|---|
| `designed/streets_new.json` | 16 条街（id、name、cookname、cookshortname、desc） | `streets_new.json` |
| `designed/foods_new.json` | 23 种食材；只保留 foods 已有字段，丢掉 recommendLevel、levelRef、reason、premiumOf、usedBy* 这些说明字段 | `foods_new.json` |
| `designed/street_medals_new.json` | 16 枚勋章，字段同 goods；丢掉 `_src` | `street_medals_new.json` |
| `designed/cookbooks_new.json` | 1479 道菜，1~10 品级；不含 coin/level/desc | `cookbooks_new.json` + §5.3 生成 |
| `designed/cookbooks_price_new.json` | 新菜的 coin、level、desc（单独一个文件，重跑导入时整份替换，不用去老文件里挑出来删） | `cookbooks_new.json` 拆出来 |
| `designed/street_medal_map.json` | 30 条街各对应一枚勋章：`{ streetId, goodsId }` | 老街 140~150、187~189；新街 92014~92029 |

- `source.ts` 加上这些文件。
- `build.ts` 把它们和 dataset 里对应的列表拼起来，再走原有校验。拼接时 id 冲突报错。

### 5.2 导入脚本

`packages/config/scripts/import-new-streets.ts`（用 tsx 运行）：

- 参数是 `data/新街道菜谱` 目录。读取后按上表拆分、去掉说明字段、生成 8~10 品级，写出上面这些文件。
- 另一个 agent 以后重跑数据后，再运行一次就能整份替换。

### 5.3 8~10 品级生成规则

规则从老菜谱（修订后 2331 道）统计得来，老数据的 8~10 品级来自原游戏：

- **8 品级**：沿用 7 品级的食材，普通食材 ×100，神秘食材（7 级）×20。老数据里 6/7/8 品级分别是 ×10/×25/×100，神秘食材是 ×3/×8/×20，这里一致。
- **9 品级**：每个格子按老菜谱里"同一食材在 8 品级 → 9 品级换成什么、几个"的出现次数加权抽取。不换也算一种结果，数量照老数据（普通 ×100、神秘 ×25）。
  - 例：白糖在老数据 8→9 品级有 193 次换成花雕酒 ×100。
- **10 品级**：同理，按"9 品级 → 10 品级"抽取（普通 ×100，神秘 ×32）。
- **新食材**（584~606）在老数据里没有记录：不换料，数量按上面的固定倍数。
- **同一品级里不重复出现同一种食材**：抽到重复的就在剩下的选项里重抽；都重复就不换。
- **固定随机种子**，同样输入得到同样结果。

### 5.4 街道勋章对应表

- 构建读 `street_medal_map.json`，校验：
  - 每条街恰好一行；
  - goodsId 存在且是勋章类（`type=9`）；
  - 一枚勋章不对应两条街。
- 运行时 `streetMedalId` 和 `isStreetMedal` 改用这张表，去掉 `deviceType <= 13`。
- 雕像（devicetype 20）不再有被误认的可能。

### 5.5 服务端代码

- **已学食谱补齐长度**：新增 `padLevels(levels, maxCookbookId): Uint8Array`，长度不足时补 0 到 `maxCookbookId + 1`。会写入或按全部菜谱计算的地方用它：
  - 学菜（`cookbook/service.ts`）；
  - 橱柜（`cupboard/service.ts`）；
  - 特色菜课程（`mysterious/lesson.ts`）。
- 结算和外卖不补：
  - 结算只读，按字节串实际长度遍历；外卖读品级时都带 `?? 0`。
  - 结算补了反而每轮要多复制一次。
- **探险**（`temple/explore.ts`）：神秘食材概率加上本街勋章的 `mysteriousRate`。
  - 不改成读加成汇总：灯、针、保安证本身也是勋章，读汇总会重复计算。
- **蟹老板**：`tuning.json` 的 `krabStreetMax` 改为 29。
- **模拟器**：
  - `sim/bench.ts` 的 `1 + rng.int(13)` 改为从配置的街道（除新手街）里随机；
  - `sim/bot.ts` 遍历 0~13 改为遍历配置的街道。

## 7. 风险

- **新菜谱 id 会变**：数据方案说重跑生成脚本时，新菜谱 id 会顺移。PR 2 合并后就当作固定 id；以后再增删，要求另一个 agent 固定 id。
- **数据量**：配置包会增加约 4MB 源数据，构建后的 bundle 随之变大。
  - 前端目录接口按语言只给名字，已经开了压缩；
  - 实现时量一下目录接口的大小变化，写进 PR 说明。
