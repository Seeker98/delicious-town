## 二、稳定性、性能、运维风险

- 大宗认购 `closeDue` 没有逐批 try/catch：收盘时某一批一直失败，整个区服的退款、发货都跟着停（`payOut` 排在它后面）
- 大宗认购写停更快照时先读出价、后更新批次，会漏掉停更前一刻提交的出价；写快照的短事务里先对批次行 for update（feat/ui-1011）
- 后台能取消已经过了收盘时刻、还没结算的批次（不到一分钟的窗口）
- 大宗认购“最近结果”每批单独查一次认购份数（打开多 7 条查询），可以在收盘时写进批次
- 期货交割每轮按店号取 500 张：某家店一直交割失败时，同区服店号更大的店轮不到；可以按到期时间取，或跳过本轮失败过的店
- 许愿树某家安慰奖一直失败时每分钟重试、每分钟记一条错误日志，500 家这样的会挡住后面的轮
- 分红任务每个老板一个事务（约 8 次往返），老板上千时要十几秒，会推迟这一轮的其他周期任务
- 区服数值没检查理财“一笔最多给几个包”不超过补给包的持有上限 9999：`unit` 改得很小时领取永远报“放不下”，本金卡住；加 `floor(maxTotal / unit) × perUnit ≤ maxNum` 的检查
- 发邮件、建兑换码、后台直接发称号时 lockRewardIcons 只查称号在不在、不查停用；后台直接发接口的错误路径写成 `items.icons.0.key`（fix/backlog-1010）
- 星愿：今天的星愿正好是刚下架的道具时，这一天这个区服没有星愿加成、许愿报错（现在碰不到）
- 新手大礼包：老店补领不看仓库格数，快满的仓库拆开后可能超过上限；区服后台改过 `restaurant.giftGoods` 时新店不送大礼包，补领码照样能领
- 区服关掉厨具功能后，结算体力恢复、赛厨榜防守方、外卖好友骑手的幸运三处直接读缓存加成，要等这家店下一次结算或操作才按新开关算
- 餐厅总览一个请求同时占约 9 个数据库连接（生产连接池 20），首页并发多时其他请求会排队（质量期 ③）
- 厨塔进页面同时读厨塔、赛厨榜、声望商店三份数据，可以合成一个接口（P9）
- 首页动态的 rest_log 查询和广播 12 小时截止：线上用 EXPLAIN 看一下，需要时加部分索引（feat/rest-feed）
- worker 停止时等 25 秒还没跑完就照样断开数据库、释放主节点锁，新 worker 可能在旧的还没停时开始（30 秒时会被强杀；分红按店幂等）
- preconnect 不带 crossorigin，CORS 预检可能另开连接；上线后在 DevTools 的 Connection ID 列确认（perf/1008）
- 日报的 Markdown 检查把 # 开头的行都算 Markdown（比如“#1 …”），真碰到再放宽
- 本地工具：
  - 商店整理按“整份快照”保存，没发上来的池子会被恢复成设计表；
  - 原始数据表被手改坏时报 500，不列构建错误；
  - 保存中在搜索框里输入会重画表格，改的内容保存后被清掉。
